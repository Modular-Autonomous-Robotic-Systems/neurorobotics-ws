# Cross-CLI AI directive and skill architecture

Durable record of how workspace directives (`CLAUDE.md`) and skills (`skills/`) are kept as a single source of truth reachable identically by Claude Code, Gemini CLI's successor Antigravity CLI, and any of the three driven from `agentic.nvim`, regardless of which directory a session is started in. Written 2026-08-12 while designing the `djinn`-automated symlink traversal in [../plans/antigravity-cli-integration.md](../plans/antigravity-cli-integration.md) §3.4 through §3.6. Companion to [dev-ide-ai-clis.md](dev-ide-ai-clis.md), which covers the CLIs themselves, and to [djinn-cli.md](djinn-cli.md), which covers `djinn`'s structure.

## 1. Each tool already walks the directory tree on its own

Before any symlink is added, both surviving CLIs already propagate a root-level directive file to a session started in a subdirectory, including inside the `ros_ws` submodule. This matters because it means the symlink scheme below only has to solve one problem, namely keeping `CLAUDE.md` and `GEMINI.md` identical **within a given directory**, not propagating the root file down into every submodule by hand.

Claude Code's own documentation states the mechanism plainly. "Claude Code reads CLAUDE.md files by walking up the directory tree from your current working directory, checking each directory along the way for CLAUDE.md and CLAUDE.local.md files. This means if you run Claude Code in `foo/bar/`, it loads instructions from `foo/bar/CLAUDE.md`, `foo/CLAUDE.md`... All discovered files are concatenated into context rather than overriding each other... content is ordered from the filesystem root down to your working directory." A session started inside `ros_ws/src/slam` therefore already loads `/ws/CLAUDE.md` in full at launch, with `ros_ws/CLAUDE.md` (once it exists per §3) appended after it, and any deeper nested `CLAUDE.md` loaded on demand when Claude reads files there.

Gemini CLI's engine, `gemini-cli-core`, does the equivalent walk but bounds it differently, and the bound is the load-bearing detail. `findProjectRoot`, read from the installed `dist/src/utils/memoryDiscovery.js`, climbs from the current directory looking for a `.git` **directory**.

```javascript
async function findProjectRoot(startDir) {
    let currentDir = normalizePath(startDir);
    while (true) {
        const gitPath = path.join(currentDir, '.git');
        try {
            const stats = await fs.lstat(gitPath);
            if (stats.isDirectory()) {
                return currentDir;
            }
        }
        catch (error) { /* ENOENT is expected and ignored */ }
        const parentDir = normalizePath(path.dirname(currentDir));
        if (parentDir === currentDir) return null;
        currentDir = parentDir;
    }
}
```

A git submodule's `.git` is not a directory, it is a small text file holding a `gitdir:` pointer into the superproject's `.git/modules/`, confirmed live for this workspace where `ros_ws/.git` is a 31 byte regular file. `findProjectRoot` therefore does **not** stop at `ros_ws` when a session starts there, it keeps climbing and returns `/ws`, whose `.git` is a real directory. The caller then collects `GEMINI.md` at every level from `/ws` down to the starting directory, `upwardPaths.unshift(potentialPath)` building the list root first, and separately does a breadth-first scan **downward** from the starting directory for any `GEMINI.md` nested below it. Both sets are concatenated with `concatenateInstructions`, each block wrapped in `--- Context from: <path> ---` markers, so a session started inside `ros_ws` loads `/ws/GEMINI.md` and `ros_ws/GEMINI.md` together with no extra configuration, exactly mirroring Claude Code's behaviour above. This same code path is inherited by Antigravity CLI, which shares Gemini CLI's `~/.gemini/` namespace and, per Google's own rules documentation, reads a global rules file at `~/.gemini/GEMINI.md` in addition to its primary workspace-scoped `.agents/rules/`.

The consequence is that neither tool needs to be told where the workspace root is, and the symlink work in §3 is purely about making sure that whichever of `CLAUDE.md` or `GEMINI.md` a given directory has, the other name resolves to the same bytes, so that whichever tool a session uses, the content at that level of the hierarchy is identical.

## 2. A rejected alternative: an OS-level global directive file

Both tools additionally support a directive file that loads for **every** session on the machine regardless of the working directory, entirely outside the walk-up mechanism of §1. For Claude Code this is **User instructions** at `~/.claude/CLAUDE.md`, documented as "Personal preferences for all projects... Just you (all projects)". For Gemini CLI and, by inheritance, Antigravity CLI it is the always-checked global path in `getGeminiMdFilePathsInternalForEachDir`, whose own comment reads "This part that finds the global file always runs," at `~/.gemini/GEMINI.md`.

Symlinking `/ws/CLAUDE.md` into either of those global slots was considered and rejected. Both directories are already used for exactly this kind of symlink, `~/.claude/skills/nrt-RandD-workflow` already points into `/ws/skills/`, so the mechanism would have been consistent with the existing pattern. It was rejected on two independent grounds. First, a session started anywhere inside `/ws`, which is the common case, would then load `/ws/CLAUDE.md` twice, once as the always-on global file and again through the ordinary upward walk of §1, doubling the token cost of the largest single directive file in the workspace for no benefit. Second, and more seriously, every directive in `CLAUDE.md` is specific to this workspace, the C++ member-variable prefixes of §9, the `context/` directory convention of §1, the `djinn` workflow catalogue requirement of §4, and none of it is meaningful outside `/ws`. Until 2026-08-14 this cited §8 and §3 for those two, the numbers those sections carried before `CLAUDE.md` gained its `§2, Correcting superseded claims and code` section; they are §9 and §4 respectively in the live, nine-section file. Installing it globally would inject NRT_WS-specific rules into every unrelated Claude Code or Antigravity session the operator runs anywhere else on the host, which is a correctness problem for those other sessions, not merely an efficiency one. The mechanism therefore reaches every directory **inside** the workspace by the walk-up behaviour of §1 alone, and is deliberately not installed outside it.

## 3. Pairing `CLAUDE.md` and `GEMINI.md` within a directory

### 3.1 Directories are not all the same shape

The workspace root is the case this problem was first noticed in. `/ws/CLAUDE.md` is current, 11082 bytes, and governs the whole tree. `/ws/GEMINI.md`, before this was fixed, was an independent 3668 byte file dated 2025-12-14, describing a tree that no longer existed. Two files, two authors, two dates, silently diverging, is the failure mode this section exists to close off, and the fix for the root was to make `GEMINI.md` a symlink to `CLAUDE.md`, `CLAUDE.md` being the fuller and current one.

`ros_ws`, the one submodule under this project's own control, is the opposite shape and must not be forced into the root's mould. It carries only `ros_ws/GEMINI.md`, no `CLAUDE.md`, and its content is not a copy of anything, it is a real, distinct set of commit-message conventions, subject-line and body formatting, method and file-path reference rules, specific to that submodule and absent from the root file entirely. The correct fix there is `ros_ws/CLAUDE.md` symlinked to `ros_ws/GEMINI.md`, the reverse direction from the root, because `GEMINI.md` is the one with real content in that directory.

The general rule that covers both cases without special-casing either is per directory, not global. In any directory that has exactly one of `CLAUDE.md` or `GEMINI.md`, the other name is created as a symlink to it. In a directory that has both already symlinked to each other, nothing happens, the state is already correct. In a directory that has both as **independent regular files**, exactly the divergence the root was found in, nothing is overwritten automatically, a warning is printed instead, because deciding which of two independently-authored files is canonical is a judgement call for a person to make once, as it was made here by inspecting both files' content and dates, not a rule a traversal script can safely apply. In a directory with neither file, nothing is created, because inventing a directive file out of nothing in, say, a third-party submodule the workspace does not own would be presumptuous and is out of scope.

### 3.2 Third-party submodules are excluded by construction, not by a list

`.gitmodules` names ten submodules. Besides `ros_ws`, the rest are upstream, third-party trees this project does not author directives for, `ext/calibration/kalibr` (ethz-asl), `ext/calibration/allan_variance_ros` (ori-drs), `docker/ardupilot/ardupilot_dev_docker` and `ardu_ws/src/ardupilot` (ArduPilot), `ardu_ws/src/micro_ros_agent` and `micro_ros_msgs` (micro-ROS), `sitl_ws/src/ue5/AirSim` (this project's own fork of Cosys-AirSim, but not a directory this project's own R&D happens in directly, per `ARCHITECTURE.md`'s note that Docker builds clone upstream Cosys-AirSim fresh), `sitl_ws/src/ue5/ProjectAirSim` (iamaisim), and `sitl_ws/src/ue5/UnrealEngine` (Epic). A broad workspace-wide search, pruned of `build/`, `install/`, `log/`, and equivalent generated trees, confirmed none of the nine carries a `CLAUDE.md` or `GEMINI.md`, so the rule of §3.1 is a no-op for all of them without needing to name them as an exclusion list. The one third-party file the same search turned up, `ardu_ws/src/ardupilot/AGENTS.md`, is ArduPilot's own upstream file for its own AI agent contributors and is untouched, since the pairing rule only ever acts on the `CLAUDE.md`/`GEMINI.md` pair and never touches `AGENTS.md`.

This is also why the traversal is written generically, over every path `.gitmodules` names, rather than hard-coded to `ros_ws`. A future submodule that is this project's own, and that arrives with its own `CLAUDE.md` or `GEMINI.md`, is picked up by the same rule with no script change, while a future third-party submodule with neither file remains untouched by the same rule with no script change either.

### 3.3 Nested packages inside `ros_ws`

The same broad search found `GEMINI.md` three levels deeper still, at `ros_ws/src/slam/GEMINI.md`, `ros_ws/src/sensors/GEMINI.md`, and `ros_ws/src/slam/ext/basalt/GEMINI.md`, none of which are submodule roots. These are package-level files, not workspace or submodule boundaries, and are deliberately out of scope for the `djinn`-driven traversal, which the request scoped to "sub-directories (submodule roots)". `ros_ws` carries its own `CLAUDE.md` §5 style governance already (§4 before `CLAUDE.md` gained its `§2, Correcting superseded claims and code` section), "when invoked at a submodule root, that submodule's `context/` and `plans/` govern," and by the same logic, pairing these package-level files is `ros_ws`'s own concern to solve with its own tooling if it chooses to, not something the parent workspace's `djinn` should reach into a submodule's source tree to rewrite. They are recorded here so a future traversal is not surprised by them, and so nobody mistakes their absence from the `djinn` script for an oversight.

### 3.4 The traversal itself

`git config --file .gitmodules --get-regexp '\.path$'` lists every submodule path from the file `.gitmodules` itself, without requiring the submodule to be checked out. The traversal runs inside `init_container`, against `/ws`, as part of `djinn init docker dev`, unconditionally, unlike the `docker-setup.sh`/`git-setup.sh` step immediately above it in the same branch, which only runs when a fourth argument is given, `djinn init docker dev init-git-setup` on first-time setup, and is skipped on the bare, routine `djinn init docker dev` used to refresh the image. On the setup path `ros_ws` has just been checked out by `docker-setup.sh`'s `git submodule update --recursive --remote --merge`, immediately above, in the same invocation; on the refresh path it relies on having been checked out by an earlier setup call instead, since the traversal itself does not gate on `$4`. Each path is still skipped with a directory-existence check rather than erroring the whole traversal, which covers both a submodule added to `.gitmodules` but not yet fetched and, now, a refresh call made before the workspace's first setup call ever ran. (Until 2026-08-14 this section placed the traversal in `djinn`'s first-time, host-side setup block, run directly against `$NRT_WS` before `git submodule update --init --recursive` necessarily ran, which is why the directory-existence check was written as the primary safeguard rather than a fallback; the traversal moved into `init_container`, after the submodule update, at the same date, per [../plans/antigravity-cli-integration.md](../plans/antigravity-cli-integration.md) §3.3, both because a shell method invoked from `djinn` belongs in `scripts/helpers/` rather than a standalone script, and because AI tooling reads `/ws`, never the host-only `$NRT_WS`; the `$4` opt-in guarding only the git/submodule step, not the traversal, was added the same date, directly in `djinn`, in response to the operational cost of running `--remote --merge` across all ten submodules unconditionally.)

## 4. Decomposing `CLAUDE.md` with `@` imports, not with Skills

### 4.1 Two independent always-loaded tiers exist in Claude Code, and only one of them is Skills

`CLAUDE.md` supports `@path/to/file` imports, confirmed from Claude Code's own documentation: "CLAUDE.md files can import additional files using `@path/to/import` syntax. Imported files are expanded and loaded into context at launch alongside the CLAUDE.md that references them... Splitting into `@path` imports helps organization but doesn't reduce context, since imported files load at launch." Both relative and absolute paths are supported, relative paths resolve against the file containing the import rather than the working directory, imports can nest up to four hops, and import parsing skips Markdown code spans and fenced code blocks so a path can be mentioned literally by wrapping it in backticks.

This is a materially different mechanism from a Skill. Skills are the on-demand tier, and Claude Code's own documentation draws the line explicitly: "Rules load into context every session or when matching files are opened. For task-specific instructions that don't need to be in context all the time, use skills instead, which only load when you invoke them or when Claude determines they're relevant to your prompt." A Skill's `name` and `description` frontmatter is always visible to the agent as a menu of what is available, exactly as `nrt-RandD-workflow`'s description is visible in every session of this workspace today, but the skill's body is loaded only when the agent's own judgement, matching the task against that description, decides to invoke it. `CLAUDE.md` §5 already uses this tier correctly and is the pattern to keep, "Load the `nrt-RandD-workflow` skill for the full method," a short imperative sentence in `CLAUDE.md` pointing at a Skill that is genuinely a multi-step procedure invoked when a task calls for it. Until 2026-08-14 this cited §4, the Development workflow section's number before `CLAUDE.md` gained its `§2, Correcting superseded claims and code` section; it is §5 in the live, nine-section file.

The remaining eight sections of `CLAUDE.md` are not that shape. Sections 1, 2, 3, 4, 6, 7, 8 and 9 are standing rules that must hold on every session unconditionally, the same content class `.claude/CLAUDE.md` itself already is, not a procedure an agent decides is relevant. Moving them behind Skill-invocation would make each one's enforcement depend on the agent recognising, from a one-line description alone, that a given task touches it, which is materially less reliable than the unconditional loading `CLAUDE.md` gives them today. `@` import keeps the unconditional loading, "imported files load at launch," while still moving the bulk of the text out of `CLAUDE.md` into a separate file, which is the actual thing being asked for, a shorter `CLAUDE.md` with the substance elsewhere and a pointer left behind. Until 2026-08-14 this paragraph said seven sections, listing 1, 3, 5, 6, 7 and 8, both counted against a `CLAUDE.md` snapshot from before its own §2, `Correcting superseded claims and code (MANDATORY)`, was added and, independently of that, omitting section 2 of that older, eight-section numbering (`Repo orientation`) from the list by a transcription slip; implementation against the live, nine-section file corrected both, see [../plans/antigravity-cli-integration.md](../plans/antigravity-cli-integration.md) §3.5.

### 4.2 Absolute paths, not relative ones, in the imports

`GEMINI.md` and `.agents/rules/nrt-directives.md` are both symlinks to `CLAUDE.md`, per §3 and per [../plans/antigravity-cli-integration.md](../plans/antigravity-cli-integration.md) §3.6. If `CLAUDE.md` used a relative import such as `@skills/writing-style.md`, three independent readers, Claude Code opening `/ws/CLAUDE.md` directly, Gemini CLI or Antigravity opening `/ws/GEMINI.md`, and Antigravity again opening `.agents/rules/nrt-directives.md`, would in principle need to agree on whether "relative" means relative to the real file's directory, `/ws/`, or relative to the symlink's own directory, `/ws/` again for `GEMINI.md` but `/ws/.agents/rules/` for the nested one. Every import-syntax specification read for this investigation states the relative case in terms of "the file containing the import" or "the location of the Rules file", but none was tested against a symlinked rules file specifically, and getting this wrong silently breaks only the Antigravity path while Claude Code and Gemini CLI continue to work, which is exactly the kind of divergence this whole effort exists to close off. Every import in `CLAUDE.md` is therefore written as an absolute path, `@/ws/skills/writing-style.md`, which resolves identically no matter which of the three names is opened to reach it, closing off the ambiguity rather than depending on all three implementations agreeing on it.

### 4.3 Where the section content moves

Each of `CLAUDE.md`'s nine sections becomes a heading followed by either a Skill pointer, for §5 alone, or a single absolute `@` import, for the other eight. `skills/` was chosen as the target directory per the request, but the eight extracted files are plain Markdown without `name`/`description` frontmatter, deliberately not shaped as invokable Skills, since they are meant to load unconditionally through the import rather than be offered to the agent's on-demand judgement, and giving them Skill frontmatter would list them in the same always-visible menu as `nrt-RandD-workflow` while their content is not itself a procedure to invoke. The eight files and the section each is drawn from verbatim, with no summarisation, are `skills/context-system.md` (§1), `skills/correcting-superseded-claims.md` (§2), `skills/repo-orientation.md` (§3), `skills/working-conventions.md` (§4), `skills/no-hard-wrap-formatting.md` (§6), `skills/code-change-discipline.md` (§7), `skills/writing-style.md` (§8), and `skills/cpp-naming-conventions.md` (§9). Until 2026-08-14 this listed only seven files and numbered them against the older, eight-section `CLAUDE.md`; `skills/correcting-superseded-claims.md` is the addition, per the same correction as §4.1 above.

### 4.4 A further opportunity, noted but not taken here

`.claude/rules/` supports the same `paths:` YAML frontmatter used for path-scoped loading, "Path-specific rules... only apply when Claude is working with files matching the specified patterns," which would let `cpp-naming-conventions.md` load only when a `.cpp`/`.h`/`.hpp` file is touched rather than in every session regardless of language. This is a genuine, Claude Code specific efficiency gain over a plain `@` import, and `.claude/rules/` is documented to support symlinks for exactly this kind of sharing, "Share rules across projects with symlinks... Symlinks are resolved and loaded normally." It is not adopted in this pass, because Gemini CLI's and Antigravity's own import and rules mechanisms, per §1 and per Google's rules documentation, do not document an equivalent conditional-loading feature, so taking it would make Claude's C++ naming enforcement path-scoped while Gemini's and Antigravity's stayed unconditional, a parity break in when the rule is present rather than in what the rule says. Recorded here as a specific, ready-to-take next step should Claude-only efficiency become worth that asymmetry.

## 5. Summary of what is git-tracked versus djinn-recreated

`CLAUDE.md` itself, the eight extracted `skills/*.md` files, `GEMINI.md` as a symlink, and `.agents/rules/nrt-directives.md` and `.agents/skills/nrt-RandD-workflow` as symlinks, all live under `/ws` outside any gitignored directory, so git stores every one of them, including the symlinks themselves, natively, and a fresh clone reproduces the whole arrangement with no `djinn` step required for those paths specifically. The one path that is genuinely host state and cannot be committed is `~/.claude/skills/nrt-RandD-workflow`, because it lives inside `$NRT_WS/.claude`, which `.gitignore` excludes since that directory is the bind-mounted credential store shared with the running container, and that is precisely why its symlink is created by `djinn init docker dev` rather than by `git`, per [../plans/antigravity-cli-integration.md](../plans/antigravity-cli-integration.md) §3.3, discussed further in §3.6.

## 6. `djinn` runs on the host, AI tooling runs in the container

A principle this design leans on repeatedly, worth stating once on its own rather than only implicitly through §3 and §4: `djinn` itself is a host-side script, invoked by the operator's own shell, where `$NRT_WS` is the workspace root; every container it builds mounts that same directory at `/ws`, and `$NRT_WS` is unset inside all of them, confirmed by grep across every Dockerfile in the tree. Claude Code, `agy` and `agentic.nvim` are only ever invoked from inside one of those containers, so a file path written for one of them to read, or a script whose behaviour is meant to mirror what one of them would see, has to be `/ws`, never `$NRT_WS`, regardless of what `djinn`'s own, host-side variable is named.

This is not a new distinction invented for this design. `scripts/helpers/sitl.sh`'s `list_projectairsim_games` already documents it directly for a different function, taking the workspace root as a parameter rather than reading it from the environment, "`$1` is the workspace root, `$NRT_WS` on the host or `/ws` inside `airsim2_container`, which is why it is a parameter rather than read from the environment." `sync_directive_pair`, added in [../plans/antigravity-cli-integration.md](../plans/antigravity-cli-integration.md) §3.3, follows the identical shape for the same reason, and the traversal that calls it is deliberately invoked through `iexec` into a running container, against `/ws`, rather than executed by `djinn`'s own shell against `$NRT_WS`, even though the two paths reach the same underlying files through the bind mount, because the operations it wraps, `git-setup.sh` and `docker-setup.sh`, already assume a container's view of the tree and cannot be run correctly from the host at all.
