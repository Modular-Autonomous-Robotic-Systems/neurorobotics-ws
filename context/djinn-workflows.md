# `djinn` workflow & test catalogue

Durable, AI-facing catalogue of every `djinn` workflow: its invocation, the call chain (helper functions + scripts) it drives, the side effects (containers/images/files) it produces, the expected outcome, and a validation/test strategy. It exists so the (currently manual) validation of these workflows can be **automated later** without re-deriving intent from source. **Maintenance rule (also in `CLAUDE.md §4`): every new or changed `djinn` workflow MUST be added/updated here in the same change.** Seeded 2026-07-24 from the SITL workspace-mounting migration — see [sitl-workspace-migration.md](sitl-workspace-migration.md) and [djinn-cli.md](djinn-cli.md).

Grammar: `djinn <verb> <subject> <args>`. Helpers are sourced from `scripts/helpers/{data,exec,docker,sitl,ai}.sh`. Runtime containers mount `$NRT_WS` → `/ws` (`scripts/start.sh`). Current image `VERSION=0.1.0` (`.djinn_config`).

## Legend for "Test strategy"
Because these cannot run in the dev container, each entry lists a **precondition**, an **action**, and an **observable assertion** an automated harness can check (exit code, file existence, `ros2 pkg prefix`, `djinn ps`, log grep).

## SITL workflows (primary focus of the migration)

### `djinn build ardupilot-sitl`
- **Call chain:** `spawn_container_if_needed sitl_bridge_container nrt:$VERSION` → `iexec_ros sitl_bridge_container "/ws/ardu_ws/scripts/build.sh"`.
- **Script:** `ardu_ws/scripts/build.sh` → `source /opt/ros/humble/setup.bash`; `cd /ws/ardu_ws`; `rosdep install --from-paths src -y --ignore-src --rosdistro humble`; `colcon build --cmake-args -DBUILD_TESTING=ON`.
- **Sources:** submodules `ardu_ws/src/{ardupilot,micro_ros_agent,micro_ros_msgs}` (5 ROS 2 packages; ardupilot's are under `Tools/ros2/`).
- **Side effects:** creates `/ws/ardu_ws/{build,install,log}`.
- **Expected:** colcon builds all packages; `/ws/ardu_ws/install/setup.bash` exists.
- **Test:** *precond* submodules populated + `sitl_bridge_container` runnable → *action* run command → *assert* exit 0; `docker exec sitl_bridge_container bash -lc 'source /ws/ardu_ws/install/setup.bash && ros2 pkg prefix ardupilot_sitl'` prints a path.

### `djinn build airsim-sitl`
- **Call chain:** `spawn_container_if_needed sitl_bridge_container` → `iexec_ros sitl_bridge_container "/ws/sitl_ws/scripts/build.sh"`.
- **Script:** `sitl_ws/scripts/build.sh` → `cd /ws/sitl_ws/src/ue5/AirSim`; download rpclib (`external/rpclib`) + Eigen (`AirLib/deps/eigen3`) if absent; `cd /ws/sitl_ws`; `rosdep install --from-paths src/ue5/AirSim/ros2/src src/ue5/ProjectAirSim/ros/projectairsim_ros2_cpp …`; `colcon build --base-paths src/ue5/AirSim/ros2/src src/ue5/ProjectAirSim/ros/projectairsim_ros2_cpp --cmake-args -DCMAKE_BUILD_TYPE=Release`.
- **Critical scoping:** discovery is restricted to `src/ue5/AirSim/ros2/src` so the AirSim submodule's ROS 1 (catkin) tree under `ros/` and its stale `ros2/{build,install,log}` artifacts are **not** discovered (would otherwise break/duplicate). See [sitl-workspace-migration.md](sitl-workspace-migration.md) gotcha 2.
- **Second base path added 2026-08-03.** The Project AirSim ROS 2 bridge builds from the same invocation. The **package** directory is named rather than its parent `src/ue5/ProjectAirSim/ros`, because that parent also holds `node` and `examples`, both catkin, and discovering either reproduces exactly the failure the AirSim scoping was introduced to prevent. Note also that `ros/projectairsim_ros2_cpp/CMakeLists.txt:73-83` pulls in `client/cpp` by `add_subdirectory`, and `client/cpp/CMakeLists.txt:24-86` fetches nlohmann JSON, msgpack, Eigen and NNG from the network at configure time, so the first build needs network access from inside the container. That is a departure from the Cosys-AirSim build, whose only downloads are the two explicit `wget` calls at the top of the same script.
- **Runtime dependencies:** `projectairsim_ros2_cpp` adds `nav_msgs`, `rclcpp_action` and `rosgraph_msgs` over `airsim_ros_pkgs`. All three are core `ros_base`-tier packages (`docker/ros/Dockerfile`'s `ros-humble-ros-base` install), already present on every architecture regardless of the `ros-humble-desktop-full` arm64 gate described in [ros-deps-workspace.md](ros-deps-workspace.md), so no image change is needed. This was checked by reading `package.xml` directly rather than through `rosdep install --simulate`, because a misspelled dependency key is invisible to the latter — gotcha 6 of [sitl-workspace-migration.md](sitl-workspace-migration.md). (Previously attributed to `ros-humble-desktop`/`ros-humble-desktop-full` at `docker/ros/Dockerfile:15-16`; corrected 2026-08-16 after the arm64 gate work showed these three are `ros_base`-tier and the line numbers had shifted.)
- **Side effects:** creates `/ws/sitl_ws/{build,install,log}`; downloads into the AirSim submodule tree.
- **Expected:** builds `airsim_ros_pkgs`, `airsim_interfaces` and `projectairsim_ros2_cpp`; `/ws/sitl_ws/install/setup.bash` exists.
- **Test:** *assert* build log does **not** mention `airsimros`/`projectairsim_ros`/`fm_msgs`; `ros2 pkg prefix airsim_ros_pkgs` and `ros2 pkg prefix projectairsim_ros2_cpp` both succeed; `/ws/sitl_ws/install/setup.bash` present.

### `djinn up sitl_bridge`
- **Call chain:** `spawn_container_if_needed sitl_bridge_container nrt:$VERSION` → `iexec_ros … /ws/ardu_ws/scripts/build.sh` → `iexec_ros … /ws/sitl_ws/scripts/build.sh`.

### `djinn start sitl [orbslam3|basalt]`
- **Bare `start sitl`:** `start_simulation nature` (spawns `airsim_container`) → `spawn_container_if_needed sitl_bridge_container` → three `gnome-terminal`s: AirSim (`sitl_ws/scripts/run_airsim.sh`), SITL bridge (`ardu_ws/scripts/run_ardupilot_airsim_ros_sitl.sh` → `iexec_sitl sitl_bridge_container "ros2 launch controllers sitl.launch.py use-sim-time:=True"`), and QGroundControl (`ext/QGroundControl.AppImage`).
  - **`use-sim-time:=True` added 2026-07-28.** It makes `airsim_ros_pkgs` publish its simulator clock, remaps `/airsim_node/clock` onto the global `/clock` with a scoped `SetRemap`, binds ArduPilot's `--use_sim_time` to it, and sets the `use_sim_time` parameter on `managed_logger_node`. Without it AirSim and ArduPilot stamp from rate-locked but origin-independent clocks, several seconds apart, and VISLAM cannot pair a frame with an inertial sample. The argument defaults to `False` everywhere it is declared, so dropping it from this invocation restores the pre-2026-07-28 behaviour exactly, which is the intended way to reproduce a historical run. See [`sitl-time-synchronisation.md`](sitl-time-synchronisation.md) and [`/ws/plans/sitl-clock-synchronisation.md`](../plans/sitl-clock-synchronisation.md).
- **`orbslam3` / `basalt`:** `spawn_container_if_needed nrt_container` → `iexec_sitl2 nrt_container "ros2 launch …"` (the SLAM stack against AirSim topics).
- **`basalt` (`djinn:267-283`):** launches `controllers basalt_slam_test.launch.py` with `log-level`, `ap_status_topic_name`, `camera-topic`, `calibration-file-path`, `configuration-file-path:=…/sitl_config_vo.json` (a VIO config despite the `_vo` name), `slam-type:=VISLAM`, `use-sim-time:=True` and `imu-topic:=/ap/imu/experimental/data`. **This workflow starts SLAM only** — the simulator, ffmpeg encoder and managed recorder come from `djinn start sitl`, which must already be running.
  - **`use-sim-time:=True` added 2026-07-28.** It sets `use_sim_time` on `basalt_slam_node` only, forwarded through `basalt_slam.launch.py`, so the compute node's own output stamps land in the same domain as the camera and inertial stamps it consumes. `basalt_controller` deliberately does **not** get it, because its lifecycle-transition watchdog reads `self.get_clock().now()` and a stalled `/clock` would leave a failed transition latched in flight forever. This argument must be paired with `use-sim-time:=True` on `djinn start sitl`, since nothing publishes `/clock` otherwise and a sim-time node with no clock reports time zero. Note the spelling: no space after `:=`, `ros2 launch` splits on whitespace first, so `use-sim-time:= True` is two tokens and fails the launch.
  - **History (2026-07-25 → 2026-07-26).** `basalt_slam_test.launch.py` used to include `sitl.launch.py`, so `djinn start sitl basalt` brought up a *second* AirSim bridge, ArduPilot SITL, encoder and `managed_logger_node` on top of the persistent ones. Two recorders racing for `/ws/data/telemetry` make the loser's `on_activate` throw `Database directory already exists`. The include was removed 2026-07-26 and the file is now SLAM-only.
  - Six arguments were dropped from this invocation at the same time: `ap_type`, `output_bag_name` and `topics_to_record` (recorder settings — now owned solely by `sitl.launch.py`, pass them to `djinn start sitl`), and `input_topic`, `ffmpeg_topic`, `ffmpeg_node_name` (never declared by any file in this chain; the encoder's topics are hardcoded in `sitl.launch.py`). All six would now be silently discarded, since `ros2 launch` does not warn about undeclared arguments.
  - `ap_type` was separately corrected from `ArduPilot` to `ardupilot` on 2026-07-25; the old value matched nothing and left the stack with no `/ap/status` subscriber. It now lives only in `sitl.launch.py`'s chain. Change-record: [`/ws/plans/basalt-slam-defect-remediation.md`](../plans/basalt-slam-defect-remediation.md) Changes 3.3/3.4.
- **`orbslam3` (`djinn:265`):** runs `ros2 launch slam orbslam3.launch.py`. **This workflow is broken (2026-07-25):** `ros_ws/src/slam/launch/` contains only `basalt_slam.launch.py`; there is no `orbslam3.launch.py`. The ORB-SLAM3 stack is launched instead via `controllers/launch/slam_controller.launch.py`. The `-DSLAM_TYPE=ORBSLAM3` configure failure (`slam/CMakeLists.txt`, empty `install(TARGETS …)`) was fixed 2026-07-25, but the workflow is still broken: the missing launch file remains, and `controllers/controllers/slam/mono_driver_node.py:40-46` still uses `MultiThreadedExecutor` without importing it.
- **Overlays:** `iexec_sitl`/`iexec_sitl2` source `/opt/ros/humble`, `/ws/ardu_ws/install`, `/ws/sitl_ws/install`, `/ws/ros_ws/install`.
- **Test:** *assert* the three terminals launch; the bridge process runs with no "setup.bash: No such file"; for SLAM, the launch node appears in `ros2 node list`. For `basalt`, additionally *assert*:
  - **exactly one** of each shared node exists after `djinn start sitl` **and** `djinn start sitl basalt` are both up — `ros2 node list | grep -c managed_logger_node` returns `1`, and likewise for the AirSim bridge and the ffmpeg encoder. This is the regression test for the duplicate bring-up removed 2026-07-26; before the fix the count was 2 and the second recorder failed with `Database directory already exists`.
  - `ros2 param get /video_logging_controller ap_type` returns the value passed to **`djinn start sitl`** (not to `basalt`, which no longer carries it) — proves the surviving forwarding chain `sitl.launch.py` → `target_recorder.launch.py`.
  - `ros2 topic info -v /ap/imu/experimental/data` shows a **matched** subscriber (proves QoS compatibility — `ros2 node info` alone does not, see [`ardupilot-dds-qos.md`](ardupilot-dds-qos.md)).
  - `/clock` has exactly one publisher, `airsim_node`, at roughly 100 Hz; the SITL console prints `Using \clock topic for DDS timing: enabled`; `ros2 param get /basalt_slam_node use_sim_time` and `/managed_logger_node use_sim_time` return `true` while `/basalt_controller` and `/video_logging_controller` return `false`; and a contemporaneous `/ap/imu/experimental/data` stamp and camera stamp agree to within 50 ms. Relaunching without `use-sim-time` must reproduce the multi-second offset, which is the revert-path check.
  - `ros2 lifecycle get /managed_logger_node` reports `unconfigured` after launch and becomes `active` **on arming, before any takeoff**; and the first `/ap/status` message in the resulting bag carries `armed: true, flying: false`. That last one is the end-to-end proof that the trigger message itself was recorded.
- **Teardown:** `djinn kill sitl` (stops bridge/sim/QGC).

### `djinn up airsim [env]` / `start_simulation`
- **Call chain:** `start_simulation <env>` → `spawn_container_if_needed airsim_container nrt_airsim:0.0.1 x86_64` → (for `airsim_container`) `source $NRT_WS/sitl_ws/scripts/start.sh airsim` which `docker run … -v <envs>:/ws … airsim_container`.
- **Calling convention changed 2026-08-03.** `sitl_ws/scripts/start.sh` used to take the UE `Environments` directory as `$1`, and it now takes a target name, one of `airsim` or `airsim2`, from which it derives the mount, the image and the container name. It defaults to `airsim`, so a caller written against the old convention still reaches the Cosys-AirSim container. The `airsim` branch reproduces the previous `docker run` exactly, including the `-v $(pwd)/settings.json:/home/ue4/Documents/AirSim/settings.json` bind. Note that `$(pwd)` is `$NRT_WS` because `djinn` cds there before sourcing, so that mount binds `$NRT_WS/settings.json`, which is an empty directory rather than a file. It is inert, because `run_airsim.sh` always passes `-settings=/ws/settings.json` which resolves inside the `Environments` mount, and it was preserved verbatim rather than corrected so that the Cosys-AirSim path behaves exactly as before.
- **Test:** *assert* `airsim_container` running; `/ws` inside it is the UE `Environments` dir.

### `djinn init docker airsim2 [mode] [base_image]`
- **Argument scheme changed 2026-08-14.** `$4` was a base-image override; it is now a three-way rebuild-mode selector, and the base-image override moved to `$5`, read only when `$4` is non-empty. Until this date `$4` carried the override directly, so `djinn init docker airsim2 ghcr.io/epicgames/unreal-engine:dev-5.7` was the override form; that form no longer skips the engine build, since `$4` is no longer read as an image reference. The replacement form is `djinn init docker airsim2 rebuild-wrapper ghcr.io/epicgames/unreal-engine:dev-5.7` (see the modes below).
- **Call chain:** `$4` empty → `build_airsim2_docker_image` directly, on the default base image, skipping the engine build entirely. `$4` non-empty → `$4`'s value decides whether `docker/scripts/build_unreal.sh` runs first (see modes below), then `build_airsim2_docker_image "$5"` if `$5` is given, else `build_airsim2_docker_image` with no argument. Either way the wrapper build is `docker build "$NRT_WS/docker/airsim" --build-arg BASE_IMAGE=… -t shandilya1998/nrt_airsim:0.0.2`.
- **`docker/airsim/Dockerfile` gained a Neovim IDE, Claude Code and `agy` since 2026-08-16**, matching `docker/dev`, so `build_airsim2_docker_image` itself now wraps that `docker build` with `setup_nvim_config_for_image_build "$NRT_WS/docker/airsim"` before it and `cleanup_nvim_config_after_image_build "$NRT_WS/docker/airsim"` after, staging `docker/dev/*.lua` into the build context exactly as `djinn`'s own `nrt` branch does for `docker/base`. No `djinn` grammar change, since every `$4` mode above funnels through this one function. Unlike `docker/base`/`docker/dev`, this Dockerfile installs Claude Code and `agy` with no `$TARGETARCH` guard, since this build is never cross-built for arm64 to begin with. The image ends on `USER ue4`, `HOME=/home/ue4`, so its `CLAUDE_CONFIG_DIR` and nvim config live under `/home/ue4`, not `/root`. See [dev-ide-ai-clis.md](dev-ide-ai-clis.md) and [dev-ide-nvim-toolchain.md](dev-ide-nvim-toolchain.md).
- **`$4` modes:**
  - *(empty)* — skip `build_unreal.sh` outright and rebuild only the wrapper on the default base image. The fast path once `shandilya1998/nrt:unreal` already exists; `$5` is not consulted in this case.
  - `force-all` — `export UNREAL_FORCE_REBUILD=1`, then run `build_unreal.sh`, which rebuilds unconditionally because of that export, then build the wrapper. This is the form `context/unreal-engine-packaging.md` §11.4 uses for the first rebuild after an engine-version pivot, since the existing image tag is reused rather than versioned and would otherwise keep serving the stale image under the same name.
  - `rebuild-base` — run `build_unreal.sh` without forcing it, so its own existence guard still applies and it only actually rebuilds `shandilya1998/nrt:unreal` if that image is missing, then build the wrapper.
  - any other non-empty value, e.g. `rebuild-wrapper` — skip `build_unreal.sh` entirely, the same effect as leaving `$4` empty, except `$5` is now consulted, so this is the form that carries a base-image override without touching the engine image.
- **Default base image changed 2026-08-04.** It was `ghcr.io/epicgames/unreal-engine:dev-5.2` and is now the locally built `shandilya1998/nrt:unreal`, because Epic's published image is Ubuntu 18.04 and Project AirSim requires 22.04. `$5` overrides it (moved from `$4` on 2026-08-14, see above).
- **Build toolchain packages changed 2026-08-05.** The apt `cmake` package is dropped (jammy resolves it to `3.22.1`, below the `3.26` the `openssl-external` `ExternalProject_Add`'s `INSTALL_BYPRODUCTS` keyword requires) and replaced with `python3 -m pip install --no-cache-dir 'cmake>=3.26,<4'` in its own layer, and `perl` is added to the apt layer for OpenSSL's own `Configure` script. Neither is a `djinn` interface change, both are internal to `docker/airsim/Dockerfile`.
- **Why executed and not sourced:** `build_unreal.sh` sets `set -e` and `set -x`, and sourcing it would leak both into `djinn`, tracing every later command and turning any subsequent non-zero exit into an abort of the CLI. A failed engine build exits rather than building Project AirSim on a missing base.
- **Why a plain `docker build` rather than `build_image`:** the Unreal Engine base image and the prebuilt ONNX Runtime tarball are x86-64 only, so the multi-platform buildx path is inapplicable.
- **Side effects:** creates image `shandilya1998/nrt_airsim:0.0.2`, and `shandilya1998/nrt:unreal` first only when `$4` is `force-all` or `rebuild-base`. Until 2026-08-14 this bullet said the bare invocation (no `$4`) built the engine image first; that stopped being true the same day, since an empty `$4` now skips `build_unreal.sh` outright.
- **Test:** *precond* `shandilya1998/nrt:unreal` exists or the preconditions of `build_unreal.sh` below are met → *action* run command → *assert* `docker images -q shandilya1998/nrt_airsim:0.0.2` non-empty; the Vulkan layer resolves `vulkan-tools`, which is the jammy name; inside the image `ls $UE_ROOT/Engine/Extras/ThirdPartyNotUE/SDKs/HostLinux/Linux_x64`, `ls $UE_ROOT/Engine/Source/ThirdParty/Unix/LibCxx/include/c++/v1` and `ls $UE_ROOT/Engine/Binaries/Linux/UnrealEditor` all succeed and `vulkaninfo --summary` reports a device; `cmake --version` inside the image reports `>=3.26,<4`; and the build log shows no missing-`perl` error at the OpenSSL configure step and no missing `libcrypto.a`/`libssl.a` link failure. *Regression* `djinn init docker airsim2 rebuild-wrapper ghcr.io/epicgames/unreal-engine:dev-5.7` must skip the engine build entirely. See [`project-airsim-docker-build.md`](project-airsim-docker-build.md) §6, §13 and §14.

### `docker/scripts/build_unreal.sh [release] [git_repo] [changelist]`
- **Not a `djinn` verb.** Invoked by the `init docker airsim2` branch above, and runnable directly. Defaults to release `5.7`. Until 2026-08-14 this line said `5.2`, unchanged since this entry was first written despite the default moving to `5.7` on 2026-08-12; the code and `context/unreal-engine-packaging.md` §11 were correct in the meantime, only this catalogue entry lagged.
- **Call chain:** guard on `docker images -q shandilya1998/nrt:unreal` → guard on `$NRT_WS/password.txt` not holding the placeholder → `docker buildx build "$NRT_WS/docker/unreal"` with `BASEIMAGE`, `GIT_REPO`, `GIT_BRANCH` and `CHANGELIST` build arguments and `username`/`password` BuildKit secrets, tagged `shandilya1998/nrt:unreal` and `--load`ed.
- **Ported from** `Engine/Extras/Containers/Dockerfiles/linux/build.sh` of `EpicGames/UnrealEngine` branch 5.2 at commit `02dc8dbdd89f749cd5500376e9bb87271bf64848`, and re-checked against branch 5.7 at commit `0bcfaffa52e9557258dbd388835ac7668fe864a4` when the default moved, finding the two upstream files differ in exactly one line, the `BASEIMAGE` default, which the script now resolves per release rather than as a constant; see `context/unreal-engine-packaging.md` §11.2. Branch resolution is upstream's, so a value with a dash or without exactly two dots is a branch name outright, making `5.2` resolve to branch `5.2` while `5.2.1` resolves to tag `5.2.1-release`.
- **Credentials:** `$NRT_WS/username.txt` and `$NRT_WS/password.txt`, both gitignored. The password file holds a GitHub personal access token whose account must be linked to Epic Games. SSH keys do not substitute, because the Dockerfile's clone step mounts BuildKit secrets and `git-credential-helper-secrets.sh` reads them from `/run/secrets`.
- **Side effects:** creates image `shandilya1998/nrt:unreal`. Never pushed, because the image embeds the Unreal Engine and the licence forbids redistribution. This is why `docker/scripts/docker-build.sh`, whose `--push` is unconditional, is not reused.
- **Cost:** compiles an Installed Build from source with `-set:WithDDC=true`, on the order of 200 GB and four or more hours per `sitl_ws/src/ue5/ProjectAirSim/docs/development/dev_setup_linux.md:83`. The existence guard exists precisely so this is never repeated implicitly; `UNREAL_FORCE_REBUILD=1` opts back in.
- **Test:** *precond* the Docker daemon's filesystem has space for an Installed Build, and `password.txt` holds a real token → *action* run script → *assert* `docker images -q shandilya1998/nrt:unreal` non-empty; `docker run --rm shandilya1998/nrt:unreal cat /etc/os-release` reports Ubuntu 22.04; `ls /home/ue4/UnrealEngine/Engine/Binaries/Linux/UnrealEditor` succeeds; the log shows no `add-apt-repository` failure. *Idempotence* a second run prints the skip message and exits without rebuilding.

### `djinn up airsim2 [env]` / `start_simulation2`
- **Call chain:** `start_simulation2 <env>` → `xhost +local:docker` → since 2026-08-16, the same `mkdir -p $NRT_WS/.claude $NRT_WS/.gemini` / `touch $NRT_WS/.claude.json` (if absent) prep `djinn init docker dev` does, needed now that `docker/airsim/Dockerfile` carries Claude Code and `agy` → `spawn_container_if_needed airsim2_container nrt_airsim:0.0.2 x86_64` → `source $NRT_WS/sitl_ws/scripts/start.sh airsim2` which `docker run … -v $NRT_WS:/ws … -v $NRT_WS/.gemini:/home/ue4/.gemini -v $NRT_WS/.claude:/home/ue4/.claude -v $NRT_WS/.claude.json:/home/ue4/.claude.json … airsim2_container`. The `airsim` (Cosys-AirSim) branch of the same script mounts none of these, since `shandilya1998/nrt_airsim:0.0.1` carries no IDE.
- **Differs from `airsim`:** mounts the whole workspace root at `/ws` rather than only the UE `Environments` directory, matching every other runtime container, so that the game binary, the scene configuration and the build script are reachable by absolute path. No settings bind mount, because Project AirSim has no settings file and no `-settings=` flag.
- **Test:** *assert* `airsim2_container` running; `/ws` inside it is the workspace root; `ls /ws/sitl_ws/config/airsim2` lists the scene and robot configs.

### `sitl_ws/scripts/build_airsim2_game.sh [project] [config]` (inside `airsim2_container`)
- **Not a `djinn` verb.** Run with `djinn exec airsim2 "…"` or `docker exec`. Defaults `StonePineForest` and `Development`.
- **Call chain:** guard on `unreal/Blocks/Plugins/ProjectAirSim/SimLibs` → `./build.sh simlibs_release` if absent → `RunUAT.sh BuildCookRun` with `-archivedirectory=packages/<project>/<config>` → `chmod +x` on the staged binaries.
- **Why the guard:** the sim libs must exist before Unreal Build Tool runs, because the plugin links their static archives by path out of `SimLibs`. This is the cause of upstream issues 83 and 129.
- **Side effects:** creates `sitl_ws/src/ue5/ProjectAirSim/{build,packages}` and populates `SimLibs`. The first build needs network access from inside the container, because `client/cpp/CMakeLists.txt:24-86` fetches nlohmann JSON, msgpack, Eigen and NNG at configure time.
- **Test:** *assert* exit 0; the build log shows `simlibs_release` completing and no `standalone_sim` link error; `packages/StonePineForest/Development/Linux/StonePineForest/Binaries/Linux/StonePineForest` exists and is executable, which is the exact path `run_airsim.sh airsim2` invokes.

### `djinn start sitl2 [orbslam3|basalt]`
- **Bare `start sitl2`:** `start_simulation2 nature` → `spawn_container_if_needed sitl_bridge_container` → three `gnome-terminal`s: ProjectAirSim (`sitl_ws/scripts/run_airsim.sh airsim2`), a **10 second** sleep, SITL bridge (`ardu_ws/scripts/run_ardupilot_airsim_ros_sitl.sh airsim2` → `iexec_sitl sitl_bridge_container "ros2 launch controllers sitl2.launch.py use-sim-time:=True"`), and QGroundControl.
- **Why 10 seconds and not 3:** the startup ordering is inverted relative to Cosys-AirSim. The game starts with no scene and the bridge loads one, so the bridge must reach a running simulator, and `projectairsim_ros2_cpp_node`'s constructor **throws** on a failed connect at `projectairsim_ros2_cpp_node.cpp:152-155`. A premature connection is fatal rather than merely delayed. If it still fails, raise this sleep rather than the 3 s `TimerAction` inside the launch file.
- **`sitl2.launch.py` versus `sitl.launch.py`:** the AirSim bridge include becomes a `Node` action, because `projectairsim_ros2_cpp` ships no launch file, the `/clock` remap group disappears, because the bridge already publishes on the global `/clock`, and a new `ardupilot-params` argument defaults to `/ws/sitl_ws/config/airsim2/project-airsim-quad.parm` and is **appended** as a fourth entry to the ArduPilot `defaults` list. Everything else, including the 3 s timer, the encoder, the recorder and every `/ap/*` argument, is copied verbatim.
- **Topic compatibility:** the node remaps `/ProjectAirsim/StonePineForestArduCopter/robots/Copter/sensors/front_center/scene_camera` onto `/airsim_node/Copter/front_center_Scene/image`, so every downstream consumer, the encoder, ORB-SLAM3 and Basalt, needs no edit and the `orbslam3`/`basalt` sub-branches are byte-identical to the `sitl` ones. That identity is what makes the two simulators comparable on the same SLAM inputs.
- **Test:** *precond* `djinn init docker airsim2`, `build_airsim2_game.sh` and `djinn build airsim-sitl` have all run → *action* run command → *assert* the game listens on 8989 and 8990 (`lsof -i :8989 -i :8990`); the bridge logs `Connected to Project AirSim` and `Loaded Project AirSim scene`; `ros2 topic list` shows the camera under the remapped name; `ros2 topic hz /clock` reports one publisher at ~200 Hz; `param show ATC_RAT_RLL_P`, `SCHED_LOOP_RATE`, `FRAME_TYPE`, `MOT_THST_HOVER` return 0.733, 185, 1, 0.461, which proves the four-file `defaults` list layered in the intended order; the copter spawns on terrain and holds a stable altitude, which is the spawn-origin check; and it reports a healthy GPS and arms, which is the end-to-end proof of the ArduPilot JSON contract and the first real test of whether the unproven ArduPilot path works at all.
- **Teardown:** `djinn kill sitl2`.

### `djinn kill sitl2 [basalt]` / `djinn down airsim2`
- **Bare `kill sitl2`:** `stop_sitl_container` → `stop_simulation2` (stops `airsim2_container`) → `terminate_process QGroundControl` → kill `projectairsim_ros2_cpp` in `nrt_container`.
- **`kill sitl2 basalt`:** identical to `kill sitl basalt`.
- **`kill airsim2`:** greps the game binary name `StonePineForest` rather than `airsim_lib`.
- **`down airsim2`:** `docker stop airsim2_container && docker rm airsim2_container`, mirroring the `airsim` case which also names its container explicitly.
- **Test:** *assert* `airsim2_container` gone from `djinn ps`; no `projectairsim_ros2_cpp_node` in `ros2 node list`; and crucially `djinn start sitl` afterwards still works unchanged, which is the regression test for the whole migration.
