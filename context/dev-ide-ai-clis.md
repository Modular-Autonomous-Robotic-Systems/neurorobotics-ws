# Agentic CLIs in the dev IDE

Durable record of the agentic coding CLIs installed into the Neovim IDE images, of where each stores credentials and looks for workspace directives and skills, and of how each is driven from inside the editor over the Agent Client Protocol. Companion file to [dev-ide-nvim-toolchain.md](dev-ide-nvim-toolchain.md), which covers the editor and its system dependencies. Written 2026-08-12; the Gemini-to-Antigravity replacement itself was implemented 2026-08-14.

## 1. The two CLIs and the transition that forced the change

Claude Code is installed in `docker/base/Dockerfile`, `docker/dev/Dockerfile` and, since 2026-08-16, `docker/airsim/Dockerfile` too, all from `https://claude.ai/install.sh`, with `CLAUDE_CONFIG_DIR` set immediately after so that credentials resolve to the bind-mounted directory rather than to a location inside the container filesystem, `/root/.claude` in the first two and `/home/ue4/.claude` in `docker/airsim`, since that image ends on `USER ue4`. `docker/base` and `docker/dev` build for `linux/amd64,linux/arm64` through `docker buildx`, and since 2026-08-16 this install, and the Antigravity CLI install below, run only when `$TARGETARCH = amd64`, `ARG TARGETARCH` being buildx's own predefined build argument for the platform currently being built. Neither CLI is needed on arm64 hardware at present, so the install is skipped there outright rather than worked around, per direct instruction after the defect below was diagnosed; a future need for either CLI on arm64 requires revisiting §1.1. `docker/airsim/Dockerfile`'s Claude Code/`agy` installs carry no such guard, and do not need one, since `build_airsim2_docker_image` in `scripts/helpers/sitl.sh` runs a plain `docker build`, never `buildx --platform`, the Unreal Engine base image and the ONNX Runtime tarball both being x86-64 only (`context/project-airsim-docker-build.md` §2). The Dockerfile does declare `ARG TARGETARCH` since 2026-08-16, but only for its Neovim/`fzf` architecture branch, unrelated to this gate, see [dev-ide-nvim-toolchain.md](dev-ide-nvim-toolchain.md) §1.

Gemini CLI is no longer installed. Until 2026-08-14 it was the npm package `@google/gemini-cli` on the shared global install line in both images, and `djinn` carried the acknowledgement `# TODO gemini-cli is DEPRECATED need to replace with agy` immediately above its login line. Google retired Gemini CLI for free and consumer tiers on 2026-06-18, together with the Gemini Code Assist IDE extensions for those tiers, while organisations holding Code Assist Standard or Enterprise licences retain access indefinitely; a Standard or Enterprise licensee who still wants it can reinstate the npm package without touching anything else in this file. Both the npm line and the TODO were removed per [../plans/antigravity-cli-integration.md](../plans/antigravity-cli-integration.md) §3.9.

Antigravity CLI, binary `agy`, is Google's replacement and shares the agent harness of the Antigravity 2.0 desktop application. It is installed in both Dockerfiles from `https://antigravity.google/cli/install.sh`, immediately after the Claude Code install and `CLAUDE_CONFIG_DIR` line, amd64-only per §1.1 below. That installer was read in full rather than trusted from documentation, and it is POSIX shell under `set -euo pipefail`, takes no interactive input, resolves a per-platform manifest, verifies a SHA512 checksum before installing and aborts on mismatch, writes the binary to `$HOME/.local/bin/agy`, and finishes with `agy install` which configures the shell environment only. Its own comments describe this final step as a "Go-Native Setup Trigger", consistent with `agy` being an ahead-of-time-compiled Go binary rather than a JIT runtime, which matters for §1.1. Nothing in it needs a terminal, so it is safe in a Dockerfile `RUN`. Both images already place `/root/.local/bin` on `PATH`, added originally for `ruff`.

### 1.1 Why the arm64 leg of the build cannot run either installer under QEMU

Diagnosed 2026-08-16 from a real build failure. `docker/base/Dockerfile`'s and `docker/dev/Dockerfile`'s `linux/arm64` leg, built via `docker buildx build --platform linux/amd64,linux/arm64` on an x86_64 host, runs every `RUN` instruction under QEMU user-mode emulation through `binfmt_misc`, since no native arm64 builder is attached. `install.sh`, read in full from `https://claude.ai/install.sh`, downloads a versioned, SHA256-checksummed standalone `claude` binary and then unconditionally executes `"$binary_path" install ${TARGET:+"$TARGET"}`, propagating its exit code, with no flag to skip that step. That binary is Bun-compiled (JavaScriptCore), and the observed failure was `panic(main thread): Segmentation fault at address 0x1100` from Bun v1.4.0 on `linux arm64`, `install_code=139` (SIGSEGV), which `install.sh` correctly surfaces as a failed `RUN` rather than swallowing.

The mechanism is a documented QEMU aarch64 user-mode emulation defect class, not an arm64 support defect in Claude Code or in Bun specifically. A JIT runtime mmaps a page writable, writes machine code into it, then makes it executable and jumps into it; QEMU's user-mode emulator translates guest code into cached host translations and must invalidate that cache when the underlying guest page is rewritten, and the JIT-write-then-execute sequence is exactly the case multiple QEMU aarch64 issues report as missed, producing a segfault on the corrupted/stale translation. `docker/buildx#3170` ("Cross-compiling for linux/arm64 causes segmentation fault on hosts with Linux kernels newer than 6.8.0-49-generic") reports the identical pattern; this workspace's build host reported kernel `6.8.0-136-generic` at the time of the crash, consistent with that report. Several `oven-sh/bun` issues report the same JIT/QEMU segfault triggered specifically by running Claude Code's bundled Bun binary. `agy`'s installer was checked for the same risk and is not exposed to it, being Go, ahead-of-time compiled, with no JIT page to invalidate; it was still made amd64-only alongside Claude Code, per direct instruction, since neither is needed on arm64 for now, not because `agy` itself was shown to crash.

Remediation options considered and not taken, recorded so a future need for either CLI on arm64 does not have to rediscover them: building the arm64 leg on native arm64 hardware or a native arm64 buildx node (`docker buildx create --append`) rather than under QEMU, which sidesteps the whole defect class rather than one crash; retrying the `RUN` instruction, since some reports describe the crash as intermittent, though this build's failure was not observed to be; and pinning an older Claude Code version through `install.sh`'s `TARGET` argument in case an earlier bundled Bun avoids it, unverified and a moving target. None was taken because arm64 support for either CLI was not needed at the time this was diagnosed.

The `agy-acp` and `claude-agent-acp` npm packages on the shared `npm install -g` line remain installed on both architectures, since installing a pure npm package does not execute either CLI's own binary and was not implicated in the crash; on arm64 they are consequently present but inert, since the binaries they wrap are absent there.

## 2. Where each CLI keeps state, and why one bind mount covers two of them

`docker/scripts/start_ide.sh` and `scripts/start.sh` mount three host paths for this purpose.

```
-v $NRT_WS/.gemini:/root/.gemini \
-v $NRT_WS/.claude:/root/.claude \
-v $NRT_WS/.claude.json:/root/.claude.json \
```

These are live bind mounts and not copies, verified by `stat` reporting `/ws/.claude` and `/root/.claude` as the same device and inode, and likewise for `/ws/.gemini`, with `/proc/mounts` listing each target. Anything written on either side is the same file.

`sitl_ws/scripts/start.sh`'s `airsim2` branch mounts the identical three host paths, since 2026-08-16, but into `/home/ue4/...` rather than `/root/...`, because `airsim2_container` runs `docker/airsim/Dockerfile`'s image, which ends on `USER ue4`. The `mkdir -p $NRT_WS/.claude $NRT_WS/.gemini` / `touch $NRT_WS/.claude.json`-if-absent prep that guards against a missing `.claude.json` being auto-created as a directory by the mount, previously only in `djinn`'s `init docker dev` branch, is duplicated into `start_simulation2()` in `scripts/helpers/sitl.sh` for the same reason. The script's `airsim` (Cosys-AirSim) branch mounts none of this, since that image, `nrt_airsim:0.0.1`, carries no IDE and no CLI.

Antigravity writes into two directories and both sit beneath `~/.gemini/`, so the existing Gemini mount already covers it and no additional `-v` is required. The private application data directory `~/.gemini/antigravity-cli/` holds `settings.json`, `history.jsonl`, `cache/projects.json`, `log/cli-*.log` and the OAuth token file `antigravity-oauth-token`. The shared configuration directory `~/.gemini/config/` holds `hooks.json`, `projects/`, `agents/`, `plugins/` and the globally discovered `skills/`. The split between the two is itself the subject of several upstream changelog entries, one of which corrects the `/agents` panel for having displayed `~/.gemini/antigravity-cli/` when the directory actually scanned at startup is `~/.gemini/config/`.

A quirk of this workspace follows from the mount layout. Gemini CLI distinguishes user-scope settings at `~/.gemini/settings.json` from workspace-scope settings at `<cwd>/.gemini/settings.json`, but because `$NRT_WS` is mounted at `/ws` and `$NRT_WS/.gemini` is mounted at `/root/.gemini`, those two paths are the same file here and the distinction collapses.

## 3. Antigravity login persistence, and the fixed bug that appears not to be

Antigravity login does persist across container recreation given the mount above. This is worth stating plainly because the evidence most readily found online says the opposite.

`google-antigravity/antigravity-cli#479`, titled "File-based token storage is write-only, fresh process rejects a valid antigravity-oauth-token in headless Linux containers", is still open, and reports with `strace` evidence that a fresh process opens and reads the token file and then still reports that the user is not logged in. Its labels name the affected versions, `1.0.10` and `1.0.13`. The defect is real but it was fixed, and the issue simply was not closed. The upstream `CHANGELOG.md` entry for 1.1.3, dated 2026-07-16, which is also the date of the issue's last activity, reads that the release "Fixed repeated sign-in prompts on Linux caused by the OS keyring, the CLI now bypasses the keyring when no D-Bus session bus is present (headless hosts and containers), skips it for an hour after a timeout, and uses longer keyring timeouts so a slow-but-successful credential read is no longer cut short and forced into a fresh login". Release 1.1.12 of 2026-08-11 then raised the keyring read timeout from one second to five, having found the shorter value caused a fallback to empty storage and a forced re-login. The related `#57`, reporting the same symptom on WSL and in containers, was closed as fixed in 1.0.1.

The rule to carry forward is that any container of version 1.1.3 or later stores and reads the token from the file store because no D-Bus session bus is present, so the mount is sufficient. A regression here would show as a sign-in prompt on a container that has already been authenticated, and the version should be checked before the issue is treated as new.

## 4. Where each CLI looks for workspace directives and skills

The directives that govern work in this repository live in `CLAUDE.md`, and each CLI discovers instructions at a path of its own choosing.

Claude Code reads `CLAUDE.md`.

Gemini CLI reads `GEMINI.md`, confirmed from the installed package where `DEFAULT_CONTEXT_FILENAME = 'GEMINI.md'` at `@google/gemini-cli-core/dist/src/tools/memoryTool.js:17`. It can be pointed elsewhere through the `context.fileName` setting, which accepts a single name or a list, the list branch being visible at `memoryTool.js:22-28` where `setGeminiMdFilename` tests `Array.isArray`, fed from `settings.context?.fileName` at `@google/gemini-cli/dist/src/config/config.js:336`. The documentation bundled inside the package gives the example `{"context": {"fileName": ["AGENTS.md", "CONTEXT.md", "GEMINI.md"]}}`.

Antigravity reads workspace rules from `.agents/rules`, retaining `.agent/rules` for backward compatibility, and its global rules file is `~/.gemini/GEMINI.md`. Google documents a limit of 12000 characters per rules file. `CLAUDE.md` stood at 11082 bytes when this was written, which is about 92 percent of that budget, so the ceiling is close enough to matter and should be checked before any substantial addition.

For skills, Claude Code discovers them beneath `~/.claude/skills/` and `.claude/skills/`. The workspace skill is exposed to it by a symlink, `/root/.claude/skills/nrt-RandD-workflow` pointing at `/ws/skills/nrt-RandD-workflow`. That symlink cannot be created in a Dockerfile, because the `$NRT_WS/.claude` bind mount masks whatever the image places at `/root/.claude`, so it has to be created on the host side or at container start. Antigravity discovers workspace skills at `.agents/skills/` in the same `SKILL.md` with `name` and `description` frontmatter format. Its global skills location is documented on Google's plugins page as `~/.gemini/antigravity-cli/skills/`, while the changelog correction noted in §2 points at `~/.gemini/config/`, and independent testing found `~/.gemini/config/skills/`, `~/.gemini/antigravity-cli/skills/` and `~/.gemini/skills/` all recognised with `~/.gemini/antigravity/skills/` not recognised. Symlinked customization directories are supported, one changelog entry having fixed rules being loaded twice when a rules directory was reachable through a symlink.

A trap recorded so it is not repeated. `GEMINI.md` at the repository root was, until this was addressed, a divergent copy dated 2025-12-14 of 3668 bytes against `CLAUDE.md`'s 11082, describing a tree that no longer existed and naming `nvim-gemini-companion/`, `ext/ardupilot` and `envs/` as current, and containing none of the context system rules, the mandatory development workflow, or the writing and C++ naming conventions. Duplicating a directive file guarantees this outcome. The single source of truth is `CLAUDE.md` and every other consumer should reach it through a version-controlled symlink at whatever path that consumer documents.

## 5. Driving the CLIs from Neovim over ACP

`agentic.nvim` spawns an agentic CLI as a subprocess speaking the Agent Client Protocol, newline-delimited JSON-RPC 2.0 over stdio. Its configuration is `docker/dev/ai.lua`, which by §1 of the companion file governs both images.

User options are merged into the plugin's defaults by a recursive `deep_merge_into` at `lua/agentic/utils/object.lua:4-15`, reached through `merge_config` and `Agentic.setup`. The plugin ships a default table of thirteen providers in `lua/agentic/config_default.lua`, each carrying `name`, `command`, `args` and `env`, `gemini-acp` among them with `args = { "--acp" }`. `docker/dev/ai.lua`'s `acp_providers` no longer overrides `gemini-acp`, removed alongside Gemini CLI per [../plans/antigravity-cli-integration.md](../plans/antigravity-cli-integration.md) §3.9, which simply leaves that shipped default unselected rather than breaking anything, since the entry was only ever an override. No Antigravity provider exists among the thirteen, so the new `agy-acp` entry is written in full, `command = "agy-acp"`, since there is nothing to inherit for a provider the plugin ships no default for. A partial entry, such as the surviving `claude-agent-acp` override, inherits whatever fields it omits from the shipped default.

Whether the workspace directives reach an agent driven this way depends on the adapter. For Claude they do. The adapter constructs its Claude Agent SDK query with `systemPrompt = { type: "preset", preset: "claude_code" }` and `settingSources: ["user", "project", "local"]`, at `dist/acp-agent.js:4082` and `4156` of the installed package. The SDK's own type declarations at `sdk.d.ts:1900-1910` document that this controls which filesystem settings load, listing `user` as `~/.claude/settings.json`, `project` as `.claude/settings.json` and `local` as `.claude/settings.local.json`, and state that a caller "Must include `'project'` to load CLAUDE.md files". The adapter includes it, so `CLAUDE.md` loads and the user-scope skills symlink is in scope. The separate `resolveSettings({ settingSources: [] })` at `dist/index.js:47` is a policy resolution and does not govern the session query, so it should not be mistaken for isolation mode.

Both Dockerfiles now install `@agentclientprotocol/claude-agent-acp`, the renamed successor to the deprecated `@zed-industries/claude-agent-acp`, npm having reported of the old name that it "has been renamed to @agentclientprotocol/claude-agent-acp. Please migrate to continue receiving updates". Its last publish was 0.23.1 on 2026-03-26 while the renamed package reached 0.66.0 on 2026-08-07. The binary name `claude-agent-acp` is unchanged across the rename, so no configuration references the old name and the migration was confined to the npm install line, applied 2026-08-14 per [../plans/antigravity-cli-integration.md](../plans/antigravity-cli-integration.md) §3.10. Until that date an image rebuild would have installed the abandoned package even though the live container this file was originally written against had the renamed one, since a manual installation of the newer package shadowed it at `/usr/local/bin/claude-agent-acp`.

Antigravity has no native ACP mode. The upstream request `google-antigravity/antigravity-cli#31` was opened 2026-05-20 and remains open with 176 comments and activity as recent as 2026-08-11. Driving `agy` from the editor therefore requires a third-party adapter, and the two credible candidates compared on 2026-08-11 were `shindgew/agy-acp`, published to npm as `agy-acp` requiring Node 22 or later and wrapping the real `agy` binary through a pseudo-terminal, and `shubzkothekar/antigravity-acp`, which is more widely starred but requires a Bun runtime and whose own README warns that use with personal Antigravity OAuth credentials may violate Google's Terms of Service and risks account suspension. The former was chosen for those reasons. It remains an unofficial single-maintainer project carrying no vendor endorsement. Because it wraps the real binary, whatever `agy` discovers from `.agents/rules` and `.agents/skills` in the working directory applies to a session driven from the editor, though that follows from the wrapper's mechanism rather than from any documented guarantee and is worth re-checking after an adapter upgrade.

## 6. Authenticating each CLI non-interactively enough to be scripted

The `init docker dev` branch of `djinn` prepares the config directories, then, inside `init_container`, optionally runs `git-setup.sh` and `docker-setup.sh`, gated behind a fourth positional argument so that only the first, explicit `djinn init docker dev init-git-setup` touches git and submodule state and every later, bare `djinn init docker dev` used to refresh the image does not, then unconditionally syncs the `CLAUDE.md`/`GEMINI.md` directive symlinks across the workspace and its submodule roots, both against `/ws` rather than the host's `$NRT_WS` since that is what a container-side process actually sees (see [ai-directive-architecture.md](ai-directive-architecture.md) §6), and only then triggers each CLI's interactive authentication once through a real terminal, `iexec` being `docker container exec -it` at `scripts/helpers/exec.sh:5-7`.

For Antigravity the invocation to use is `agy -p '/usage'` rather than a bare `agy`. It authenticates, because quota cannot be reported without an identity, so an unauthenticated run enters the sign-in flow exactly as a bare launch would. It exits by itself, whereas a bare `agy` opens the full terminal interface and holds the calling script until a human quits it. And it is free and idempotent, because the 1.1.9 changelog entry records that print mode answers the read-only slash commands `/usage`, `/quota`, `/credits`, `/model`, `/effort` and `/skills` directly, "without starting an agent turn, spending quota, or leaving a conversation behind". The sign-in itself survives `docker exec -it` because release 1.1.2 added pasting the OAuth authorization code through the controlling terminal, `/dev/tty` on POSIX, when stdin is consumed by a piped prompt, and made only genuinely terminal-less runs fail fast with an actionable message rather than block. A container entered with `-it` has a controlling terminal and so takes the paste path.

The same print mode is the cheapest way to verify the directive and skill wiring from a script, since `agy -p "/skills"` lists the discovered skills without starting an agent turn.
