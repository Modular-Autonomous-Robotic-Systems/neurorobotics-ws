# `/ros_deps_ws` — fixed ROS 2 dependencies baked into the image

Durable record of the migration that moves the two fixed, never-changing ROS 2 build dependencies — `vision_opencv` and `ros2_shared` — out of the `ros_ws` workspace (where they were git submodules) and into a dedicated overlay workspace `/ros_deps_ws` baked into the Docker `ros` image. Change date: 2026-07-24.

## Why

`vision_opencv` (provides `cv_bridge`, `image_geometry`, `vision_opencv`) and `ros2_shared` are upstream packages that are pinned and are not meant to evolve with the project. Carrying them as submodules of `ros_ws` meant every clone/`submodule update` pulled them and every `colcon build` rebuilt them. Baking them into the image once — in the shared `ros` layer, inherited by `pangolin`/`camera`/`ardupilot` — makes them available across **all** ROS 2 workspaces (`ros_ws`, `ardu_ws`, `sitl_ws`) and all use cases, with no per-workspace source or rebuild.

## The model

- **Image layer:** `docker/ros/Dockerfile` (after the `libi2c-dev`/`tf2` install, before `ulimit`) clones the two repos into `/ros_deps_ws/src` and `colcon build`s them:
  - `git clone -b humble https://github.com/ros-perception/vision_opencv.git`
  - `git clone -b master https://github.com/clydemcqueen/ros2_shared.git`
  - build: `source /opt/ros/humble/setup.bash && rosdep install --from-paths src -y --ignore-src --rosdistro humble && colcon build --cmake-args -DCMAKE_BUILD_TYPE=Release`, wrapped in `/bin/bash -c "…"` because Dockerfile `RUN` defaults to `/bin/sh` and `setup.bash` requires bash. Preceded by `apt-get update` (rosdep resolves `cv_bridge`'s OpenCV to system `libopencv-dev`); `/var/lib/apt/lists` cleaned after.
  - `rosdep` is already `init`/`update`d earlier in the same Dockerfile; `colcon` is already installed. Placement after those is required.
- **Entrypoints:** both `docker/ros/ros_entrypoint.sh` and `docker/ardupilot/ros_entrypoint.sh` `source /ros_deps_ws/install/setup.bash` immediately after `source /opt/ros/$ROS_DISTRO/setup.bash`. Unconditional (no existence guard) because the overlay is baked into the image and always present — unlike the `/ws/{ardu_ws,sitl_ws}` mount-built trees, which are existence-guarded.
- **Build scripts** source the overlay so it is on `AMENT_PREFIX_PATH` at compile time:
  - `scripts/build_ros_packages.sh` (the one `djinn build nrt`/`up`/`start` invokes) sources `/ros_deps_ws/install/setup.bash` before the `ros_ws` `colcon build`.
  - `ardu_ws/scripts/build.sh` and `sitl_ws/scripts/build.sh` source it after `/opt/ros/humble/setup.bash` (defensive/consistent; those workspaces do not directly depend on the two packages today).

## Consumers (why the overlay must be sourced before `ros_ws` builds)

`ros_ws` packages `find_package` the removed deps and now resolve them from the overlay: `src/sensors` (`cv_bridge`, `image_geometry`), `src/slam` (`cv_bridge`), `src/tello/tello_driver` (`cv_bridge`), `src/flight_matrix_bridge` and `src/controllers` (`ros2_shared`). If `/ros_deps_ws/install/setup.bash` is not sourced, these fail with missing-package CMake errors.

## Gotchas / non-obvious facts (verified 2026-07-24)

1. **Nested submodule removal.** `ros_ws` is itself a submodule of the superproject; `vision-opencv`/`ros2_shared` were submodules **of `ros_ws`** (declared in `ros_ws/.gitmodules`, git-dirs under `.git/modules/ros_ws/modules/src/…`). Removal was done inside `ros_ws` via `git submodule deinit -f … && git rm -f …` (which also strips the `.gitmodules` stanzas and `.git/config` sections), plus `rm -rf` of the stale `.git/modules/ros_ws/modules/src/{vision-opencv,ros2_shared}`. This is a change to the `ros_ws` submodule repo — the superproject now sees `ros_ws` as modified until that is committed there.
2. **SSH → HTTPS.** The task specified `git@github.com:` URLs, but in-image `git clone` has no SSH key and would fail; all other in-image clones use `https://github.com/…`. The Dockerfile therefore uses HTTPS. Upstreams as specified: `ros-perception/vision_opencv`@`humble`, `clydemcqueen/ros2_shared`@`master`.
3. **Bash-only source in `RUN`.** `source /opt/ros/humble/setup.bash` fails under the default `/bin/sh`; the build `RUN` wraps the source+rosdep+colcon in `/bin/bash -c "…"` rather than setting a global `SHELL` (keeps the change local, avoids altering child-image `RUN` shells).
4. **`camera` image build is unaffected.** `docker/camera/build_camera_ros.sh` builds only `camera_ros` (libcamera-based) at image-build time and does not depend on `cv_bridge`/`ros2_shared`; it needs no overlay source.
5. **`ros_ws/build_ros_packages.sh`** (a copy inside the submodule) is **not** the script `djinn` runs — `djinn` calls the superproject `scripts/build_ros_packages.sh` (`djinn:164,187,195,200`). Only the superproject copy was updated.

## `ros-humble-desktop-full` arm64 gate (2026-08-16)

`docker/ros/Dockerfile` builds multi-arch via `buildx --platform linux/amd64,linux/arm64` (the same mechanism documented for `docker/base`/`docker/dev` in [dev-ide-ai-clis.md](dev-ide-ai-clis.md)). The plain `apt-get install ros-humble-desktop-full` line (previously unconditional) can fail on the arm64 leg with `E: Unable to locate package ros-humble-desktop-full`, even on a rebuild of a Dockerfile that previously built successfully for both architectures. This is not an apt-key/signing problem, the build gets well past `apt-get update` and installs hundreds of `ros-humble-desktop` packages first.

**Root cause.** `ros-humble-desktop-full`'s real dependency tree, fetched from the authoritative source (`https://raw.githubusercontent.com/ros2/variants/humble/<variant>/package.xml`), is `desktop_full` → `desktop` + `perception` + `simulation` + `ros_ign_gazebo_demos`. `desktop` is already installed unconditionally by the preceding `ros-humble-desktop` line, so `desktop-full` only *adds* `perception` (`image_common`, `image_pipeline`, `image_transport_plugins`, `laser_filters`, `laser_geometry`, `perception_pcl`, `vision_opencv`) and `simulation` (`ros_ign_bridge`, `ros_ign_gazebo`, `ros_ign_image`, `ros_ign_interfaces`, the Ignition Gazebo ROS bridge, **not** Gazebo Classic/`gazebo11`) plus `ros_ign_gazebo_demos`. The ROS buildfarm has a documented history of arm64 legs of dependency chains transiently vanishing from the package index after a sync (precedent: [ROS 2 Iron ARM64 packages vanished](https://discourse.openrobotics.org/t/ros2-iron-arm64-packages-vanished/38652), July 2024, ~105 packages, one arm64 build failure in an unrelated package cascaded through dependents and self-healed on the next sync); `simulation`/Ignition Gazebo's arm64 leg is the most likely candidate to regress this way given Gazebo's general arm64 fragility, which is why a Dockerfile that built cleanly for arm64 in the past can fail on a later, otherwise-unchanged rebuild.

**What is actually needed.** Cross-referencing `perception`'s and `simulation`'s package lists against every `package.xml` under `ardu_ws/src/ardupilot`, `sitl_ws/src/ue5/ProjectAirSim/ros`, `ros_ws/src` (and, for completeness, the sibling `sitl_ws/src/ue5/AirSim/ros2/src` that the same `sitl_ws/scripts/build.sh` colcon-builds), only two `desktop-full`-exclusive packages are load-bearing today:
- `image_transport` (from the `image_common` repo, part of `perception`), needed by `ros_ws/src/sensors`, `ros_ws/src/slam`, `ros_ws/src/controllers`, and `sitl_ws/src/ue5/AirSim/ros2/src/airsim_ros_pkgs`.
- `camera_calibration_parsers` (also `image_common`/`perception`), needed by `ros_ws/src/tello/tello_driver`.

Nothing in these trees references `ros_ign_*`/Ignition Gazebo, `laser_filters`, `laser_geometry`, `perception_pcl`/`pcl_ros`, `image_pipeline`, or `image_transport_plugins` today, but the gate below installs the entire `perception` variant on arm64 regardless, rather than only these two packages, so a future package under any of these three trees can pick up any `perception` package without the gate needing to be revisited (Gazebo/Ignition `simulation` is deliberately excluded regardless, since it is not supported on arm64 in this workspace). `cv_bridge`/`image_geometry` (also nominally part of `perception`'s `vision_opencv`) are **not** needed from `desktop-full` regardless of this decision, because they are already built from source into the `/ros_deps_ws` overlay documented above, decoupled from the apt metapackage entirely. `octomap`/`octomap_ros`/`octomap_msgs` (needed by `slam`, `frontier_detection`) are likewise not part of `desktop-full`'s tree at all, they come from an explicit, separate `apt-get install` in `docker/camera/Dockerfile:62`, four layers downstream of `docker/ros`, and are unaffected by this gate either way.

`ros_ws/src/tello/tello_gazebo` depends on `gazebo`/`gazebo_ros`/`gazebo_ros_pkgs`, Gazebo **Classic**, which was never part of `desktop-full`'s tree for Humble in the first place (confirmed from the same `simulation`/`package.xml` fetch) and is not installed anywhere in the image chain. Verified live: on 2026-08-16 its colcon build fails at CMake configure (`Could not find a package configuration file provided by "gazebo"`), a standing, pre-existing failure independent of architecture or this gate; `install/tello_gazebo` contains only the ament index marker files, no `lib/`. Per [sitl-time-synchronisation.md](sitl-time-synchronisation.md)'s `use_sim_time` audit, `tello_gazebo` does not participate in `djinn start sitl`, so this failure does not block the active SITL pipeline; colcon continues past it since no other package depends on it.

**The gate.** `docker/ros/Dockerfile` now takes `ARG TARGETARCH` and installs the full `ros-humble-desktop-full` metapackage only when `$TARGETARCH = amd64`; on arm64 it installs the full `ros-humble-perception` metapackage instead, the other constituent of `desktop-full` besides `simulation`, rather than only the two packages actually referenced today, so perception-related additions to `ardu_ws`/`sitl_ws`/`ros_ws` are covered without a future revisit of this gate. `simulation` is excluded on arm64 unconditionally, both because nothing here uses it today and because Gazebo/Ignition simulation is not a supported workflow on arm64 in this workspace. `ros-humble-perception` has a confirmed arm64 build (the official `arm64v8/ros:humble-perception-jammy` Docker Hub image installs it directly, which only succeeds if the apt package resolves on arm64), with no known arm64 gap analogous to `simulation`/Ignition Gazebo's. `ros-humble-ros-base` and `ros-humble-desktop` remain unconditional on both architectures, so nothing that already resolved from those tiers is affected. (Between 2026-08-16 revisions this gate briefly installed only `ros-humble-image-transport ros-humble-camera-calibration-parsers` on arm64, the minimal set then in use; broadened the same day to the full `perception` metapackage to cover future perception-related package additions without revisiting the gate, since `simulation`/Gazebo remains excluded on independent grounds regardless of the narrower or broader form.)
