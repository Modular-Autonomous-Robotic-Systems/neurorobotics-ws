# Project AirSim Docker image and build chain

Durable reference for `docker/airsim/Dockerfile`, the image `shandilya1998/nrt_airsim:0.0.2`, and everything needed to compile Project AirSim, package an Unreal environment and open the Unreal editor inside a container. Written 2026-08-03 during the Project AirSim integration, against submodule `sitl_ws/src/ue5/ProjectAirSim` at commit `7fb9c566` of 2026-07-15. The change record is [`plans/project-airsim-integration.md`](../plans/project-airsim-integration.md), the software architecture is [`project-airsim-architecture.md`](project-airsim-architecture.md), and the Cosys-AirSim counterpart, which this file deliberately does not replace, is [`airsim-docker-build.md`](airsim-docker-build.md).

## 1. What the image is, and what it deliberately is not

The image is a toolchain image. It carries the Unreal Engine, the compilers, the Vulkan runtime and the desktop libraries the editor needs, and it carries no Project AirSim source whatsoever. The source arrives through the `/ws` bind mount at container start and every compilation happens inside a running container.

Three reasons make this the only defensible arrangement, and they are recorded because the opposite arrangement is the intuitive one and was rejected deliberately. The workspace already works this way, since `ARCHITECTURE.md` §3 and [`sitl-workspace-migration.md`](sitl-workspace-migration.md) establish that workspaces are mounted rather than baked precisely so that an edit needs a recompile and never an image rebuild. The integration carries a local patch to the ROS 2 bridge, and baking a `git clone` into the Dockerfile would compile upstream instead of the patched tree, which is exactly the trap recorded at the top of [`airsim-docker-build.md`](airsim-docker-build.md), where the Cosys-AirSim Dockerfile clones upstream fresh and the local submodule's `build.sh` is not what runs. And mechanically, `docker build` cannot reach outside its build context, so a Dockerfile under `docker/airsim` cannot `COPY` from `sitl_ws/src/ue5/ProjectAirSim` without making the whole workspace the context and paying a multi-gigabyte transfer on every build.

## 2. The engine version is 5.7, and why

The base image is the locally built `shandilya1998/nrt:unreal`, which is Unreal Engine 5.7 compiled from source on an Ubuntu 22.04 userland, and the `BASE_IMAGE` build argument survives so the decision can be revisited without editing the Dockerfile. The engine version is 5.7 and the argument for it below is unaffected by which image supplies that engine.

Until 2026-08-04 this file recorded the base image as Epic's published `ghcr.io/epicgames/unreal-engine:dev-5.2`, which was correct at the time and is now wrong, because that image is built on Ubuntu 18.04 and Project AirSim's dependencies require 22.04. An artefact built before that date was produced on an 18.04 userland and is recognisable by `vulkan-utils` resolving inside it and `vulkan-tools` not. See §13 and [`../plans/project-airsim-integration.md`](../plans/project-airsim-integration.md) §3.2.1.

Until 2026-08-12 this section pinned the engine at 5.2 rather than 5.7, and the reasoning is worth keeping because it was correct on its own terms and only overridden by a later, larger cost. Project AirSim's own release binaries are cut against 5.2, evidenced by the engine banner `5.2.1-0+UE5` in the log excerpt of upstream issue 75, which is the banner a release binary prints, and running a prebuilt upstream release alongside a locally packaged game was treated as a requirement of this workspace, so that a packaged Unreal game and its plugin binaries, tied as they are to the engine version that produced them, would remain interchangeable with whatever upstream itself ships. `README.md:92` states support for 5.2 and 5.7, so both were defensible in isolation, and of the two only 5.2 also ran what upstream shipped. That requirement was set aside on 2026-08-12, once `context/unreal-engine-packaging.md` §8 diagnosed a `.umap` in `StonePineForest` saved by a newer editor than 5.2 could open, and §9 and §11 of that same file record the decision to move the whole pin to 5.7 rather than route around that one file, on the judgement that the coupling risk and rebuild cost of the move, detailed there, are worth taking against the benefit of staying interchangeable with an upstream release binary this workspace does not otherwise run.

Two further statements of the supported version exist in the tree and neither contradicts the choice. `unreal/Blocks/Blocks.uproject:3` declares `"EngineAssociation": "5.1"`, and `unreal/Blocks/Plugins/ProjectAirSim/Source/ProjectAirSim/Public/UnrealSimLoader.h:88-89` hard-codes a supported major of 5 and minor of 1, with `UnrealSimLoader.cpp:66-72` printing a startup warning for anything else. That warning is non-fatal, so a 5.2 run works while announcing an unsupported engine, and the message must not be mistaken for the cause of a later failure. This is defect G9 of [`project-airsim-architecture.md`](project-airsim-architecture.md) §G.

Note that the Cosys-AirSim image remains on `dev-5.5` through `build_airsim_docker_image` in `scripts/helpers/sitl.sh`. The two images pin different engines on purpose and neither pin may be changed to match the other.

## 3. The toolchain switch, and why the Cosys `<atomic>` failure does not recur

`CMakeLists.txt:27-39` selects the compiler purely on whether `UE_ROOT` is set in the environment. Set, the build uses the engine's bundled clang through `unreal-linux-toolchain.cmake`. Unset, it hard-codes `clang-13` and `clang++-13` from the system. Because the plugin's static archives are later linked into Unreal by Unreal Build Tool, the engine toolchain is the correct choice, and `ENV UE_ROOT=/home/ue4/UnrealEngine` in the Dockerfile is the single switch that selects it.

The consequence is that the image installs none of `clang`, `lld`, `llvm-dev`, `libc++-dev` or `libc++abi-dev`, all of which the Cosys-AirSim image at `sitl_ws/src/ue5/AirSim/docker/Dockerfile_source` does install. Cosys builds with the system clang, and Project AirSim builds with the engine clang. Adding the system compiler to this image would be inert at best and confusing at worst.

The `<atomic>` failure that cost three stacked fixes in the Cosys-AirSim image, recorded in [`airsim-docker-build.md`](airsim-docker-build.md), does not recur here, and the reason is specific rather than hopeful. Cosys-AirSim's `build.sh` smuggled `--sysroot` through `-DCMAKE_CXX_FLAGS` and supplied no C++ standard library include path, so clang had no libc++ headers. Project AirSim sets `CMAKE_SYSROOT` properly at `unreal-linux-toolchain.cmake:49-51` and then explicitly adds the engine's own libc++ include directories at `:55`, while `CMakeLists.txt:33` adds the matching library directory. That is exactly the remedy recorded as the fallback option in the Cosys context file, applied preemptively upstream.

`unreal-linux-toolchain.cmake` also globs `$UE_ROOT/Engine/Extras/ThirdPartyNotUE/SDKs/HostLinux/Linux_x64/*`, sorts, and takes the last entry, so it selects the highest installed SDK automatically. It raises a fatal error at `:26-28` when that directory is absent, which is why precondition P2 below exists.

`setup_linux_dev_tools.sh` is deliberately not executed. Its LLVM version map at `:28-33` yields a non-existent `llvm-toolchain-noble-13` suite on Ubuntu 24.04, which is upstream issues 120 and 173, and under `UE_ROOT` the system clang it installs is never used. Its package list is instead inlined, minus the clang and libc++ entries.

## 4. The `ue4` user is a requirement, not a convention

The Epic development image does not run as root, and the image must end on `USER ue4`. Its lineage is the `ue4-docker` project, whose prerequisites layer creates the account with `useradd --create-home --home /home/ue4 --shell /bin/bash --uid 1000 ue4`, clears its password, adds it to the `sudo` group and then switches to it. The same shape is visible inside this workspace, since `Dockerfile_source` installs `sudo` explicitly at `:20`, performs every `apt-get` under `USER root` at `:4`, drops to `USER ue4` at `:75` before touching the engine, and sets `ENV UE_ROOT=/home/ue4/UnrealEngine` at `:76`.

The `USER root` and `USER ue4` bracketing in `docker/airsim/Dockerfile` is therefore load bearing in both directions. Every `apt-get` needs root and the base image is not root, so without the first directive the build fails on the first layer. Without the second, the container starts as root and every engine or editor invocation writes root-owned files into `/home/ue4/UnrealEngine` and `/home/ue4/.config`, after which nothing run as `ue4` can rewrite them, and the failure appears much later as an unexplained permission error inside Unreal Build Tool rather than as a container problem.

Epic's own `Engine/Extras/Containers/Dockerfiles/linux/dev/Dockerfile` is behind the Epic licence gate but is readable over SSH with a GitHub account linked to Epic, and it is now vendored at `docker/unreal/Dockerfile`. The `useradd` line it contains confirms the account definition that the `ue4-docker` prerequisites layer and the in-workspace `Dockerfile_source` had been used to infer, so those two remain useful for the lineage they explain. The cheap way to fetch it again is `git clone --filter=blob:none --sparse` over SSH followed by `git sparse-checkout set Engine/Extras/Containers/Dockerfiles/linux`, which costs about 30 MB rather than the full engine tree.

Until 2026-08-04 this section stated that the file could not be read at all. That was wrong, and the reason it was believed is worth keeping, namely that `raw.githubusercontent.com` returns 404 for the `release` and `5.2` refs of `EpicGames/UnrealEngine`, which is true of anonymous HTTP alone and says nothing about authenticated SSH. The inference drawn from the stand-ins while the file was thought unreadable turned out to be correct.

## 5. The package inventory, layer by layer

The list is split into three `RUN` layers by purpose rather than merged, so a later reader can tell why each package is present and can drop the third entirely if the editor ever moves to a separate image. Overlap with the base image is deliberate and harmless, since `apt-get install` on an installed package is a no-op, and naming the package is worth more than saving a few seconds of build time.

| Layer | Packages | Why |
|---|---|---|
| Build toolchain | `build-essential`, `ca-certificates`, `curl`, `git`, `gnupg`, `libeigen3-dev`, `lsb-release`, `lsof`, `make`, `ninja-build`, `perl`, `python3`, `python3-pip`, `python3-venv`, `rsync`, `sudo`, `unzip`, `wget`, `zlib1g`, `zlib1g-dev` | `libeigen3-dev` short circuits the GitLab clone at `CMakeLists.txt:275-278`. `zlib1g-dev` mitigates the `libonnxruntime.so` link failure of upstream issue 173. `ninja-build` is the build driver. `perl` runs OpenSSL's own `Configure` script, invoked directly by the `openssl-external` target's `CONFIGURE_COMMAND` at `CMakeLists.txt:349-367`, since that target builds OpenSSL outside CMake's own compile machinery. `sudo` is required because `setup_linux_dev_tools.sh` and much upstream tooling assume it. `lsof` supports the port checks of validation V6. `cmake` is deliberately not in this list, see §14. |
| Vulkan | `libvulkan1`, `vulkan-tools`, `mesa-vulkan-drivers` | `-RenderOffScreen` still requires a Vulkan loader and driver, which is the diagnosis in upstream issue 75. `vulkan-tools` supplies `vulkaninfo`, which precondition P4 uses and which the base image does not carry. The name is release dependent, see below. |
| Editor desktop stack | `libfontconfig1`, `libfreetype6`, `libgtk-3-0`, `libnss3`, `libsdl2-2.0-0`, `libx11-6`, `libxcursor1`, `libxext6`, `libxi6`, `libxinerama1`, `libxrandr2`, `libxss1`, `libxtst6`, `x11-apps`, `x11-xserver-utils`, `xauth`, `xdg-utils` | The editor opens a real window on the forwarded X display. `x11-apps` supplies `xdpyinfo`, which is the first thing to run when the editor will not start. |

Until 2026-08-05 this table listed `cmake` among the Build toolchain packages and made no mention of `perl`. Both were wrong in the same audit, the first an omission that would have surfaced only once the graph defect of §14 was fixed and the OpenSSL step actually ran, the second a version too old for the build to succeed. See §14 for the full account.

The Vulkan package name is coupled to the base image's Ubuntu release and must be revisited whenever that release changes, in either direction. Ubuntu renamed the package carrying `vulkaninfo` from `vulkan-utils` to `vulkan-tools` at focal, and dropped the transitional `vulkan-utils` after focal, so on Ubuntu 18.04 only `vulkan-utils` resolves and on Ubuntu 22.04 only `vulkan-tools` does. This was discovered the hard way on 2026-08-04, when the layer failed with `E: Unable to locate package vulkan-tools` against what was then an 18.04 base. The name was changed to `vulkan-utils` at that point, and changed back to `vulkan-tools` when the base moved to 22.04, which is the value the table above now records and the correct one for the current base.

`NVIDIA_DRIVER_CAPABILITIES` is `graphics,compute,utility,display`. The `display` capability is not needed by a headless run and is required by the editor.

`EXPOSE 8989 8990` documents the NNG topic and service ports. It is documentation only, since `sitl_ws/scripts/start.sh` runs the container with `--net=host`.

## 7. The build chain inside the container

`build.sh` is a one-line wrapper that forwards its argument to `make -f build_linux.mk`, so every target below is a make target.

The coupling between the sim libs and the Unreal plugin is by file copy rather than CMake export. Every sim lib target carries a `POST_BUILD` command copying its output and headers into `unreal/Blocks/Plugins/ProjectAirSim/SimLibs/<target>/<Debug|Release>`, the destination defined at `CMakeLists.txt:70`. The sim libs must therefore exist before Unreal Build Tool is invoked, which is the root cause of the "modules are missing or built with a different engine version" reports in upstream issues 83 and 129, and the reason `sitl_ws/scripts/build_airsim2_game.sh` guards on the presence of that `SimLibs` directory and runs `./build.sh simlibs_release` when it is absent.

| Target | Depends on | Effect |
|---|---|---|
| `config_simlibs_release` | none | CMake configure of the sim libs under the engine toolchain |
| `cpp_client_release` | `config_cpp_client_release` | builds the C++ client library |
| `simlibs_release` | `config_simlibs_release`, `cpp_client_release` | builds the sim libs and copies them into `SimLibs` |
| `package_blocks_development` | `simlibs_release` | the `BuildCookRun` invocation at `build_linux.mk:261-276` that `build_airsim2_game.sh` copies in shape |
| `package_plugin` | `blocks_debuggame`, `blocks_development`, `blocks_shipping` | all three plugin configurations |

`BuildCookRun` archives into `packages/<Project>/<Config>`, which is upstream's own layout at `build_linux.mk:270` and which matters because a Development and a Shipping package of the same project would otherwise overwrite one another. Inside that directory Unreal Automation Tool stages a `Linux` tree containing the wrapper script `<Project>.sh` beside `<Project>/Binaries/Linux/<binary>`. The binary is named `<Project>` for a Development client and `<Project>-Linux-<Config>` for any other configuration, which is why a Shipping package in upstream issue 75 produced `EolicPark-Linux-Shipping`.

`sitl_ws/scripts/run_airsim.sh airsim2` invokes the staged ELF directly rather than the generated wrapper. The wrapper's only two contributions are a `chmod +x` on the staged ELF, which `build_airsim2_game.sh` now performs at build time, and forwarding the caller's arguments, which is the thing upstream issue 75 reports failing. Removing the layer removes the entire class of failure at the cost of one path component, and the failure removed is not a graceful one, because a silently dropped `-RenderOffScreen` in a container with no display manifests as a process that exits with status 1 after printing two lines. Note that the evidence is one unreproduced user report and that the wrapper is generated by Unreal Automation Tool rather than by anything in the Project AirSim tree, so no line in the repository can be cited as the cause, and upstream's own `run_sim_with_streaming.sh:27` passes flags to the wrapper on the assumption that forwarding works.

## 8. The `standalone_sim` link blocker

`samples/standalone_sim` is a member of the ALL target, and its link fails under the Unreal toolchain because the prebuilt `libonnxruntime.so` carries transitive dependencies on `libz.so.1` and the sysroot `libstdc++.so.6` that are absent from the link line, while `CMAKE_FIND_ROOT_PATH_MODE_LIBRARY ONLY` at `unreal-linux-toolchain.cmake:58` prevents resolution outside the sysroot. This is upstream issue 173, opened 2026-07-31.

The maintainer's own workaround is to comment out the live `add_subdirectory(standalone_sim)` in `samples/CMakeLists.txt`, and the file shipped with a commented-out copy of that line at `:18` immediately above the live one at `:19`, which is the hint. The workspace applies the workaround directly in the submodule working tree rather than through a `sed` in a Dockerfile or a build script, for the reason in §1, namely that a patch in the mounted tree is what actually compiles, is visible to `git diff`, and survives an image rebuild.

## 9. Local patches carried in the submodule, and their consequence

Three hunks diverge from upstream `7fb9c566`, all in the working tree of `sitl_ws/src/ue5/ProjectAirSim` with no fork and no pushed branch.

The first is the header stamping fix in `ros/projectairsim_ros2_cpp/src/projectairsim_ros2_cpp_node.cpp`, which adds a three-argument `MakeHeader` overload reading the payload's own `time_stamp` and retains the two-argument overload unchanged. It is described in [`sitl-time-synchronisation.md`](sitl-time-synchronisation.md) §Project AirSim and is defect G12 of the architecture register.

The second is the `standalone_sim` workaround of §8.

The third is `CMakeLists.txt:93`'s addition of `-lc++abi` to the Unix `add_link_options`, added 2026-08-15 against the 5.7 engine pin, described in full in §15.

The consequence to hold in mind is that the submodule reports a dirty working tree until each patch is accepted upstream or committed to a fork, and that a `git submodule update --force` would discard all three. The Unreal environment ported into `unreal/StonePineForest` is likewise untracked inside the submodule, and `.gitignore:340-347` already excludes `unreal/**/Binaries`, `Intermediate`, `Saved`, `Package`, `DerivedDataCache` and `.vscode`, but not `Content`, so roughly four gigabytes of assets appear as untracked there.

## 10. Porting an Unreal environment onto the plugin

The delta between a Cosys-AirSim project and a Project AirSim project is small and is fully documented at `docs/use_plugin.md`, with `unreal/Blocks` as the reference implementation. The steps performed for StonePineForest, which generalise, are as follows.

Copy the project without its build products, excluding `Binaries`, `Intermediate`, `Saved`, `Build`, `DerivedDataCache` and `.vscode`. Note that `rsync` is absent from the development container, so a `tar -cf - --exclude … | tar -xf -` pipeline serves in its place. Exclude any packaged-game directory as well. StonePineForest carried a 2.5 GB `Linux/` tree, the Cosys-AirSim package that `run_airsim.sh` runs for the old simulator, which is not one of Unreal's standard in-project build directories and therefore survives the standard exclude list while being useless against the new plugin.

Delete `Plugins/AirSim` and copy in all three of `unreal/Blocks/Plugins/{ProjectAirSim,Drone,Rover}`. `Drone` and `Rover` are content-only plugins carrying the meshes the simulator spawns at runtime, per `docs/use_plugin.md:9-24`, and omitting them leaves the robot invisible.

Edit `<Project>.uproject` to declare `ProjectAirSim` in place of `AirSim`, drop the `AdditionalDependencies` entry naming `AirSim`, since the plugin is not a module dependency of the game module as `unreal/Blocks/Source/Blocks/Blocks.Build.cs` demonstrates, and move `EngineAssociation` to `5.2`. Retain whatever other plugins the project declared. StonePineForest carries `ModelingToolsEditorMode` and `ChaosVehiclesPlugin` and does not carry the `SunPosition` that Blocks does.

Edit `Config/DefaultEngine.ini` to add `GlobalDefaultGameMode=/Script/ProjectAirSim.ProjectAirSimGameMode` under `[/Script/EngineSettings.GameMapsSettings]`. This is the load-bearing edit, since without it the plugin loads but never starts a simulation server.

Edit `Config/DefaultGame.ini` to replace the `/AirSim/*` cook directives with `/ProjectAirSim`, `/Drone` and `/Rover`, and to name the map under `MapsToCook`. Removing the old directives matters as much as adding the new ones, because the `/AirSim` mount point disappears with the plugin and cooking a path that no longer exists is an error rather than a warning.

Align both `Source/<Project>*.Target.cs` files with the Blocks targets, namely `DefaultBuildSettings = BuildSettingsVersion.Latest` and `IncludeOrderVersion = EngineIncludeOrderVersion.Latest`. This is required for compilation rather than cosmetic, because StonePineForest carried `BuildSettingsVersion.V5` and `EngineIncludeOrderVersion.Unreal5_5`, and neither enumerator exists in Unreal 5.2.

Retaining an existing `Source` directory conveniently satisfies step 3 of `docs/use_plugin.md`, since a project that already has a C++ module needs no dummy class generated.

The world settings game mode override, step 2B of `docs/use_plugin.md`, lives inside the binary map asset and cannot be set from a text editor. The `DefaultEngine.ini` setting alone is sufficient for a packaged headless run, so the map-level override is conditional and is performed only if the robot fails to spawn at all.

## 11. Editor procedures inside the container

`sitl_ws/scripts/start.sh` already forwards X11, since it passes `DISPLAY`, mounts `/tmp/.X11-unix` and binds the host `.Xauthority` onto `/home/ue4/.Xauthority`, so nothing new is needed for the display. The host must permit the connection, which `start_simulation2` does with `xhost +local:docker`.

```bash
djinn up airsim2
docker exec -it -u ue4 airsim2_container bash

# Confirm the display before blaming the editor. xdpyinfo comes from x11-apps.
xdpyinfo | head -3

# Confirm Vulkan, since the editor will start and then fail to render without it.
vulkaninfo --summary | head -20

$UE_ROOT/Engine/Binaries/Linux/UnrealEditor \
  /ws/sitl_ws/src/ue5/ProjectAirSim/unreal/StonePineForest/StonePineForest.uproject
```

The first open of a project with a C++ module offers to rebuild that module, which must be accepted, and which is the same compilation `build_airsim2_game.sh` performs non-interactively.

### 11.1 Reading the spawn origin from a map

Project AirSim spawns an actor at the scene configuration's `origin.xyz`, and `docs/config_scene.md:56` warns that `"0 0 0"` is the global Unreal origin and not `PlayerStart`. Cosys-AirSim spawned at `PlayerStart` by default and therefore recorded no origin anywhere, so for a landscape map the value must be read out of the map asset by hand. Getting it wrong drops the robot through the void or buries it in terrain, and the symptom is a copter that never reports a stable altitude and therefore never arms.

The conversion is exact and was read from the plugin rather than assumed. Unreal world coordinates are centimetres in a north, east, up frame, and `UnrealTransform::UnrealToNedLinear` at `unreal/Blocks/Plugins/ProjectAirSim/Source/ProjectAirSim/Private/UnrealTransforms.h:16-23` converts by `ToMeters`, a multiplication by 0.01 at `core_sim/include/core_sim/transforms/transform_utils.hpp:48-51`, followed by `NeuToNedLinear`, which negates only the third component at `core_sim/src/transforms/transform_utils.cpp:91-93`.

```
north =  UnrealX / 100
east  =  UnrealY / 100
down  = -UnrealZ / 100
```

Those three numbers in that order are the `"xyz"` string. A `PlayerStart` at X 12500, Y −3400, Z 8200 gives `"125.0 -34.0 -82.0"`.

Interactively, open the map, type `PlayerStart` in the World Outliner search box, select the actor, read Transform then Location in the Details panel, and apply the mapping. Subtract a further one to two metres from the down component, making it more negative, so the robot starts just above the surface rather than intersecting it, and set `"start-landed": true` in the actor block so it holds that position until thrust exceeds weight. `start-landed` is read at `core_sim/src/scene.cpp:1390-1391` as a sibling of `origin` and defaults to false.

Non-interactively, `sitl_ws/scripts/print_spawn_origin.py` prints the converted numbers for every `PlayerStart` in the open map and is the form to prefer, since it is reproducible and does not depend on reading a panel correctly.

```bash
$UE_ROOT/Engine/Binaries/Linux/UnrealEditor-Cmd \
  /ws/sitl_ws/src/ue5/ProjectAirSim/unreal/StonePineForest/StonePineForest.uproject \
  -run=pythonscript -script="/ws/sitl_ws/scripts/print_spawn_origin.py" -unattended -nullrhi
```

For a map with no `PlayerStart`, drag one from the Place Actors panel onto the terrain at the wanted point, at which Unreal snaps it to the surface, then read its Location as above. Any actor serves if a `PlayerStart` is unwanted, and an empty Actor is the lightest choice.

Two cross-checks are cheap and worth applying to whatever value results. The `down` component must be negative for any point above the Unreal world origin, so a positive `down` on a mountainous map is almost always a forgotten sign. And the magnitude of north and east is the horizontal distance in metres from the world origin, which is the offset from `home-geo-point`, because `JsonUtils::GetTransform` at `core_sim/src/json_utils.cpp:100-129` maps NED zero onto that geopoint and `EarthUtils::NedToGeodetic` at `core_sim/include/core_sim/earth_utils.hpp:100-125` converts from it. A value of several kilometres means the robot reports a GPS position several kilometres from the declared home, which is harmless because ArduPilot takes its home from the first fix, but which is worth recognising rather than debugging.

A third route removes the conversion entirely. `GetTransform` accepts `"geo-point": "lat lon alt"` in place of `"xyz"` at `json_utils.cpp:100-115` and performs the geodetic to NED conversion itself, which is the better form for a georeferenced terrain and the worse form for a map whose relationship to the Earth is arbitrary.

## 12. Configuration file loading, and comments in `.jsonc`

Scene and robot configuration files are loaded by `LoadJSONCFromFile` at `client/cpp/ProjectAirSimMessageLib/src/jsonc.cpp:168`, which wraps the input stream in a `jsoncbuf` filter that strips comments before nlohmann parses it. Comments in `sitl_ws/config/airsim2/*.jsonc` are therefore safe, which is not obvious from the file extension alone and is worth knowing before a comment is blamed for a parse failure.

`World::Impl::LoadSceneConfig` at `client/cpp/ProjectAirsimClientLib/src/World.cpp:1394` canonicalises the scene path, loads it, and then resolves each actor's `robot-config` against `sim_config_path`, replacing the string with the parsed document in place. The robot configuration therefore need not be named on the command line, and a relative `robot-config` resolves against `sim_config_path` rather than against the scene file's own directory.

## 13. The Unreal Engine base image, `shandilya1998/nrt:unreal` (2026-08-04)

Epic's published development images are built on Ubuntu 18.04. The evidence is direct rather than inferred, namely that `Engine/Extras/Containers/Dockerfiles/linux/build.sh:54` of branch 5.2 hard-codes `--build-arg 'BASEIMAGE=nvidia/opengl:1.0-glvnd-devel-ubuntu18.04'`. Project AirSim requires a 22.04 userland, so the engine is rebuilt locally from Epic's own Dockerfile against a 22.04 base and tagged `shandilya1998/nrt:unreal`. The full change record is [`../plans/project-airsim-integration.md`](../plans/project-airsim-integration.md) §3.2.1.

Note that the submodule's own claims about the supported Ubuntu release contradict one another, and none of them names 18.04. `Architecture.md:420` says 22.04, `README.md:19` says Ubuntu 22, both `docs_external/README.md:29` and `docs/development/use_source.md:42` say 20.04, and `.github/copilot-instructions.md:27` implies 24.04 by symlinking clang-18 onto clang-13. The 22.04 target follows `Architecture.md`, which is the most specific and the most recent.

The single most useful fact about Epic's `dev` Dockerfile is that it does not consume a local engine checkout. Its `source` stage takes `GIT_REPO` and `GIT_BRANCH` as build arguments and clones the engine inside the image with `git fetch --depth 1`, authenticated by BuildKit secrets that `git-credential-helper-secrets.sh` reads from `/run/secrets`. The build context is therefore four files totalling 32 KB, namely the `Dockerfile`, that credential helper, `set-changelist.py` and `split-components.py`. This is why `docker/unreal` vendors those four files rather than the repository carrying an Unreal Engine submodule, which would contribute several gigabytes that no build step reads. Authentication is by GitHub username and personal access token and not by SSH key, so the SSH access this workspace otherwise uses does not substitute, and the token is read from `$NRT_WS/password.txt` with the username from `$NRT_WS/username.txt`, both gitignored.

Two deltas from upstream are carried in `docker/unreal/Dockerfile`, both marked `NRT` in place. `BASEIMAGE` gains the default `nvidia/opengl:1.0-glvnd-devel-ubuntu22.04`, that tag being verified to exist while the 24.04 variant does not. And the glibc DSO patch layer is deleted, which is mandatory rather than cosmetic, because `ppa:slonopotamus/glibc-dso` publishes bionic, focal, hirsute, impish and devel and no jammy, so `apt-get update` aborts the layer on a 22.04 base. The `ENV GLIBC_TUNABLES=glibc.rtld.dynamic_sort=2` that follows it is retained on purpose, since the depth-first DSO sorting the PPA backports to glibc 2.27 landed upstream in glibc 2.35, which is what 22.04 ships, and `dynamic_sort=2` is its default there. The patch is thus redundant on jammy for the same reason it is unavailable.

The engine is compiled into an Installed Build with `-set:WithDDC=true`, which `docs/development/dev_setup_linux.md:83` puts at roughly 200 GB and four or more hours natively. Free space on the Docker daemon's filesystem is therefore a genuine precondition. `docker/scripts/build_unreal.sh` guards against repeating that cost, skipping the build when the image already exists unless `UNREAL_FORCE_REBUILD=1`, and it rejects the unedited placeholder in `password.txt` up front, because the token is not consumed until the clone step deep into the build and a forgotten token would otherwise surface only after hours. The image is never pushed, because it embeds the engine and the licence forbids redistribution, which is also why `docker/scripts/docker-build.sh` and its unconditional `--push` could not be reused.

The roughly 200 GB figure above describes one clean build's own footprint, not the cumulative disk cost of reaching one across several failed and retried attempts. During the 5.2 to 5.7 migration, `plans/unreal-engine-packaging.md` §7.4 records a fourth build attempt that ran the entire multi-hour `builder` stage clean and then failed on host `ENOSPC` assembling the final `minimal` stage, traced to Docker's BuildKit build cache compounding across three prior failed attempts against a Dockerfile that was itself edited between each one, since an edit partway through the file invalidates cache from that line forward without evicting the now-unreachable layers cached under the pre-edit content hash. `docker builder prune` between iterative build attempts, not only once a build has already failed on disk space, is the practice that finding established.

## 14. CMake version and the OpenSSL `ExternalProject_Add` byproducts gap (2026-08-05)

`CMakeLists.txt:386` passes `INSTALL_BYPRODUCTS` to the `openssl-external` target's `ExternalProject_Add`, a keyword that CMake's own `ExternalProject` module accepted only from release 3.26 onward. Ubuntu 22.04 (jammy), the base image's userland since §13, resolves the apt package `cmake` to 3.22.1, which predates that release. `ExternalProject_Add` is implemented with `cmake_parse_arguments`, whose default behaviour on an unrecognised keyword is to fold it silently into the unparsed-argument list rather than to raise an error, so the configure step neither fails nor warns. What is lost is the byproduct declaration itself, `${OPENSSL_CRYPTO_LIBRARY}` and `${OPENSSL_SSL_LIBRARY}` at `CMakeLists.txt:387`, which is how `ExternalProject_Add` tells the Ninja generator that those two files are produced by the `openssl-external` target's install step. Without it the Ninja graph carries no edge from any consumer of those paths back to that step, and a target linking `OPENSSL_CRYPTO_LIBRARY` or `OPENSSL_SSL_LIBRARY` can be scheduled to link before the still-running OpenSSL build has produced the archive, which surfaces as a missing-file link failure that reproduces intermittently under `ninja`'s parallel scheduling and not at all under a serial `make`.

The apt package is dropped from the Build toolchain layer of §5 rather than pinned by a second, versioned apt source, and CMake is instead installed with `python3 -m pip install --no-cache-dir 'cmake>=3.26,<4'` in its own `RUN` step immediately after that layer, while still `USER root` so the installed `cmake` binary lands in `/usr/local/bin`, ahead of `/usr/bin` in `PATH` and world-executable exactly as an apt-installed binary would be. `python3-pip` was already a dependency for other reasons, so this needs no new apt source, and the same command is upstream's own documented route to a working CMake, given verbatim at `docs/client_setup.md:58` and `:123` for the Windows client build, with no version floor stated there because upstream's own Windows toolchain does not carry this defect. Both bounds were checked against primary sources on 2026-08-05 rather than assumed. `packages.ubuntu.com/jammy/cmake` confirms the apt package as `3.22.1-1ubuntu1`, below the requirement. CMake's own 3.26 release notes confirm `INSTALL_BYPRODUCTS` as new in that release, added specifically so `ExternalProject_Add` install-step outputs can be declared to generators such as Ninja. And PyPI's `cmake` project page, at the time of this writing, lists 4.4.2 as its latest release, meaning an unbounded `>=3.26` floor would silently take CMake 4 rather than the newest 3.x release. The upper bound exists because of that last fact and not the first two, since CMake's own 4.0 release notes state that compatibility was removed only for `cmake_minimum_required()` calls below policy version 3.5, which clears this project's own floor of `3.15.0` at `CMakeLists.txt:18` but says nothing about the floor declared inside `nng`, `assimp`, `msgpack`, `tinygltf`, `nlohmann-json` or `googletest`, none of which is vendored in this tree to check, all being fetched fresh by `FetchContent_Declare` or `ExternalProject_Add` at configure time. The bound trades a hypothetical, unchecked risk for a small, revisitable one, namely that the pin must be revisited if a future dependency bump requires CMake 4.

`perl` is added to the same Build toolchain layer, for a reason independent of the CMake version. Every configuration of `OPENSSL_CONFIGURE_COMMAND`, both the `UE_ROOT` branch and its `else()` at `CMakeLists.txt:349-367`, invokes `<SOURCE_DIR>/Configure` directly rather than through `cmake --build`, and that `Configure` is OpenSSL's own perl script, not a CMake-generated one. This was found in the same audit as the CMake version gap, by walking every `ExternalProject_Add` and `FetchContent_Declare` in the tree, `nng`, `assimp`, `msgpack`, `tinygltf`, `nlohmann-json`, `googletest`, `onnxruntime`, `Eigen3` and `openssl`, and confirming that OpenSSL is the only one that shells out to a build tool the image did not already carry; every other dependency either goes through `cmake --build`, already covered by `cmake` and `ninja-build`, or fetches headers or a prebuilt binary. Both gaps were latent rather than active before this fix, since the graph defect meant the build had never previously reached the OpenSSL configure step at all, `perl` being absent would have been the first failure once the graph defect was corrected in isolation. The two are fixed together so that no second `docker build` is needed to discover the second gap.

## 15. SimLibs link failure against UE 5.7's toolchain, missing `-lc++abi` (2026-08-15)

`./build.sh all` inside `airsim2_container`, run fresh after `./build.sh clean` against the rebuilt 5.7 engine, reached `simlibs_unit_tests` and failed linking `core_sim_gtests`:
```
/home/ue4/UnrealEngine/Engine/Extras/ThirdPartyNotUE/SDKs/HostLinux/Linux_x64/v26_clang-20.1.8-rockylinux8/x86_64-unknown-linux-gnu/lib/gcc/x86_64-unknown-linux-gnu/8.5.0/../../../../lib64/libc++.a(stdexcept.cpp.o): undefined reference to symbol '_ZTVSt11logic_error@@GLIBCXX_3.4'
.../lib64/libstdc++.so.6: error adding symbols: DSO missing from command line
clang++: error: linker command failed with exit code 1
```
alongside a separate, non-fatal warning, `libz.so.1, needed by .../_deps/onnxruntime-src/lib/libonnxruntime.so, not found`, that names no undefined symbol and is not the cause of the failure, onnxruntime's own prebuilt binary needing a system `zlib` neither the link command's `-rpath` nor its `-L` list currently resolves, left unaddressed here since it costs the build nothing.

This was not a stale-artefact consequence of clearing the 5.2 build. `./build.sh clean` followed by `./build.sh all` rebuilt every `_deps` external project fresh, `nng-external`'s own log lines confirm a clean configure and build, and the failure is a link-time symbol resolution against the freshly compiled objects, not a mismatch between an old cached archive and a new compiler.

**Root cause.** `CMakeLists.txt:89-93`'s Unix branch compiles and links every C++ target with `-stdlib=libc++` and nothing else naming a C++ ABI library. `unreal-linux-toolchain.cmake:41-42` selects the highest-sorting SDK directory under `Engine/Extras/ThirdPartyNotUE/SDKs/HostLinux/Linux_x64`, `v26_clang-20.1.8-rockylinux8` for this engine, exactly as it did `v21_clang-15.0.1` for 5.2, so the toolchain selection itself is version-agnostic and not the defect. The failing archive path, resolved from the error, is `.../v26_clang-20.1.8-rockylinux8/x86_64-unknown-linux-gnu/lib64/libc++.a`, the clang toolchain's own bundled copy, not the one `CMakeLists.txt:33`'s `link_directories("$ENV{UE_ROOT}/Engine/Source/ThirdParty/Unix/LibCxx/lib/Unix/x86_64-unknown-linux-gnu")` explicitly names, meaning `-stdlib=libc++`'s own driver resolution on this toolchain finds and links its bundled `libc++.a` ahead of or instead of the explicit `-L` directory. `Engine/Source/Programs/UnrealBuildTool/Platform/Linux/LinuxToolChain.cs:1286-1298` was read directly from `EpicGames/UnrealEngine` branch `5.7` at this file's own pinned commit to see how Unreal's own build tool links any target against this same bundled `libc++.a`, and it never links it alone: `LinkArguments.Add("-nodefaultlibs")` is followed immediately by explicit paths to both `libc++.a` and `libc++abi.a` from the identical directory, `DirectoryReference LibCxxLibDir = DirectoryReference.Combine(LinuxInfo.BaseLinuxPath!, "lib64")` by default, falling back to the legacy `ThirdParty/Unix/LibCxx` path only when `PlatformSDK.ForceUseLegacyLibCxx()` is true, itself gated on an explicit `-ForceUseLegacyLibCxx` command-line argument nothing in this build passes. `libc++abi.a` supplies the vtables and RTTI for `std::logic_error` and its sibling exception classes that libc++'s own `<stdexcept>` implementation does not define standalone, and without it the linker falls through to the platform's default library search, finds the same symbol only inside the system's `libstdc++.so.6`, an indirect dependency reached transitively rather than named on the command line, and modern `ld` refuses to resolve a symbol against an indirect shared-library dependency it was not explicitly told to link, which is exactly the "DSO missing from command line" diagnostic. `CMakeLists.txt:96` itself carries a dormant, commented-out line, `# set(CESIUM_LINKER_FLAGS "-stdlib=libc++ -lc++abi")`, evidence that whoever wired up the (now-disabled) Cesium integration had already found and encoded this same pairing once, scoped to a target this build no longer exercises.

**Fix.** `CMakeLists.txt:93` changed from `add_link_options(-stdlib=libc++ -lanl -pthread)` to `add_link_options(-stdlib=libc++ -lc++abi -lanl -pthread)`, adding the one missing flag rather than replicating UnrealBuildTool's fuller `-nodefaultlibs` treatment, since the log's only undefined symbols are the two C++ ABI ones and every other default library, `libc`, `libm`, `libpthread`, already resolves without complaint, so the smaller, targeted change carries less risk of disturbing a currently-working link for any other target in the same `CMakeLists.txt`. This is the third local patch tracked in §9.

**Verification.** Confirmed. `./build.sh all` completed and the packaged `StonePineForest` client ran, reaching Vulkan RHI initialization, §16 below.

## 16. Vulkan device creation failure, `VK_KHR_compute_shader_derivatives` missing from driver 550.163.01 (2026-08-15)

**Symptom.** The packaged `StonePineForest` client, launched via `djinn start sitl2` → `run_airsim.sh airsim2` → the staged ELF with `-RenderOffScreen -nosound -unattended -nopause -NoSplash`, mounted every plugin and pak file correctly and reached RHI initialization, then failed:
```
LogVulkanRHI: Starting Vulkan Profile check for VP_UE_Vulkan_SM6:
LogVulkanRHI: Warning: None of the 1 devices meet all the criteria!
LogVulkanRHI: Vulkan Profile check complete.
LogRHI: Display: Skipping SF_VULKAN_SM6...
Message dialog closed, result: Ok, title: Message, text: Vulkan device could not be created at the project's supported feature levels (see log for details).
LogCore: FUnixPlatformMisc::RequestExit(bForce=true, ReturnCode=1, CallSite=<NoCallSiteInfo>)
```
The host GPU is an NVIDIA RTX 4000 SFF Ada Generation on driver 550.163.01, passed through with `NVIDIA_VISIBLE_DEVICES=all` and `NVIDIA_DRIVER_CAPABILITIES=graphics,compute,utility,display` per `docker/airsim/Dockerfile:72-73`, and `nvidia_icd.json` is present per `docker/unreal/Dockerfile`'s upstream-inherited generation step.

**Investigation.** `vulkaninfo --summary` run inside `airsim2_container` as `ue4` initially appeared to contradict the failure, listing two devices, GPU0 the NVIDIA card correctly typed `PHYSICAL_DEVICE_TYPE_DISCRETE_GPU` with `apiVersion = 1.3.277`, and GPU1 `llvmpipe`, Mesa's software rasterizer, correctly typed `PHYSICAL_DEVICE_TYPE_CPU`. This ruled out the first hypothesis, that the NVIDIA ICD was not being found at all and the game was falling back to software rendering wholesale, since the ICD, driver and loader are all demonstrably functional in that same container. `Engine/Source/Runtime/VulkanRHI/Private/VulkanRHI.cpp` was read directly from `EpicGames/UnrealEngine` branch `5.7` at this file's own pinned commit to find the exact log line's source. `LaunchEngineLoop`'s Vulkan startup calls `CheckVulkanProfile()`, which builds a temporary, profile-scoped `VkInstance` via the vendored Khronos Vulkan Profiles library (`vulkan_profiles_ue.h`, `Engine/Source/ThirdParty/Vulkan/profiles/include/`) and, if the device it selects fails `vpGetPhysicalDeviceProfileSupport()` against the `VP_UE_Vulkan_SM6` profile, aborts. `SelectPhysicalDevice()`, called internally by that check, only reaches its `"None of the %u devices meet all the criteria!"` warning after filtering out every `VK_PHYSICAL_DEVICE_TYPE_CPU` device from the enumeration; that the log reports exactly `1` device at that point, despite two being visible generally in the same container, was not resolved to an exact mechanism, but is immaterial to the outcome established next.

The generated `vulkan_profiles_ue.h` was read for `VP_UE_VULKAN_SM6`'s exact `deviceExtensions` array, fifteen required extensions: `VK_EXT_calibrated_timestamps`, `VK_EXT_descriptor_buffer`, `VK_EXT_descriptor_indexing`, `VK_EXT_mesh_shader`, `VK_EXT_mutable_descriptor_type`, `VK_EXT_scalar_block_layout`, `VK_EXT_shader_image_atomic_int64`, `VK_KHR_buffer_device_address`, `VK_KHR_compute_shader_derivatives`, `VK_KHR_maintenance4`, `VK_KHR_pipeline_library`, `VK_KHR_separate_depth_stencil_layouts`, `VK_KHR_shader_atomic_int64`, `VK_KHR_synchronization2`, `VK_KHR_timeline_semaphore`. A full, non-summary `vulkaninfo` was then run and its GPU0 (NVIDIA) 219-entry `Device Extensions` list checked against that requirement list term by term. Fourteen of fifteen are present. The fifteenth, `VK_KHR_compute_shader_derivatives`, is absent; the list instead carries `VK_NV_compute_shader_derivatives`, the vendor extension that predates it. A web search corroborated the timeline rather than leaving it to inference: `VK_KHR_compute_shader_derivatives` was only ratified into the Vulkan specification at version 1.3.295, later than driver 550.163.01's own release, so the driver cannot expose an extension name that did not yet exist when it shipped. This is a sufficient, confirmed explanation for the profile failure on its own, independent of the unresolved "1 devices" detail above, since `vpGetPhysicalDeviceProfileSupport()` requires every listed extension present and this one is categorically not.

**Root cause.** NVIDIA driver 550.163.01, current on the host, predates the Vulkan spec revision that defined `VK_KHR_compute_shader_derivatives`, and `VP_UE_Vulkan_SM6`, the profile UE 5.7 mandates for its default Vulkan feature level, requires that exact KHR-named extension. This is a host driver gap, not a container, Dockerfile, or CMake defect; every other criterion, all fourteen remaining extensions, both feature and property structs, is satisfied by this GPU.

**Fix.** Upgrade the host's NVIDIA driver to a branch that exposes `VK_KHR_compute_shader_derivatives` under its KHR name. No exact minimum version was confirmed from NVIDIA's own release notes, searched without success, but corroborating evidence places it after the `550` branch: a separate, unrelated UE 5.7 Linux Vulkan regression (`VK_ERROR_DEVICE_LOST`, `Engine/Source/Runtime/VulkanRHI/Private/VulkanPipeline.cpp`, not this workspace's issue since it is triggered by interactive editor events, PSO destruction on material recompilation, window resize, level unload, none of which a headless packaged client run through `-RenderOffScreen -unattended` exercises) was reported across drivers `570` through `610`, meaning those branches are what current UE 5.7 Linux users are actually running, and none of those reports mention a profile-check failure, implying the KHR extension is present by then. `-SkipVulkanProfileCheck`, a genuine Epic-provided command line flag (`Engine/Source/Runtime/VulkanRHI/Private/VulkanGenericPlatform.cpp`) that bypasses `CheckVulkanProfile()` entirely, was considered and rejected as the fix, since the gap is a real, confirmed missing capability rather than a false-negative check, and skipping it would only defer the same shortfall to whichever render pass first dispatches a compute shader using derivatives, a less diagnosable failure than the one already in hand.

**Verification.** Confirmed, but not sufficient by itself. The host driver upgrade to `580.173.02` (`plans/update-nvidia-driver.md`) closed exactly the gap this section describes, confirmed directly by diffing a full, non-summary `vulkaninfo` dump before and after, `VK_KHR_compute_shader_derivatives` newly present alongside the fourteen extensions that were already there. The packaged client nonetheless continued to fail identically afterward, the same `None of the 1 devices meet all the criteria!` warning, because a second, independent defect was masking the fix throughout. §17 below gives the full account.

## 17. Vulkan device creation failure, ICD manifest missing `api_version` skips the NVIDIA driver entirely (2026-08-15)

**Symptom.** After the driver upgrade of §16 closed the extension gap, `djinn start sitl2` still failed with the identical warning, `LogVulkanRHI: Warning: None of the 1 devices meet all the criteria!`, at the identical point in startup, with `vulkaninfo` still correctly reporting both the NVIDIA device and Mesa's `llvmpipe` in the same container. A `VK_ICD_FILENAMES=/etc/vulkan/icd.d/nvidia_icd.json` experiment, restricting the loader to only the NVIDIA manifest, made the failure worse rather than better, a hard crash, `vpCreateInstance(...) failed, VkResult=-9 ... with error VK_ERROR_INCOMPATIBLE_DRIVER`, rather than the graceful warning, ruling out the simplest read of the mystery, that NVIDIA was merely a lower-priority candidate among several. Removing the manifest's `api_version` field entirely, on the reasoning that modern Vulkan loaders treat it as optional and query the real driver directly, changed nothing, the identical graceful warning persisted, disproving that theory too.

**Investigation.** `VK_LOADER_DEBUG=all` against the actual packaged client launch settled it directly, rather than continuing to infer from outside. The active loader is confirmed as UE's own bundled copy (`INFO: Vulkan Loader Version 1.4.304`, distinct from the system loader also detected and logged, `1.3.204`, and then explicitly discarded per `LogVulkanRHI: Display: Using included Vulkan loader.`). Its own manifest parser reads, verbatim: `WARNING | DRIVER: loader_parse_icd_manifest: ICD JSON /etc/vulkan/icd.d/nvidia_icd.json does not have an 'api_version' field. Skipping ICD JSON.` NVIDIA's ICD is rejected wholesale at manifest-parsing time, before any `dlopen` of `libGLX_nvidia.so.0` is even attempted, whenever the field is absent. With NVIDIA out of consideration, the trace shows exactly what fills the gap: `VirtIO` fails `vkCreateInstance` outright (return code `-3`, no virtual GPU present), `Intel`, `Intel HASVK` and `RADV` are each removed by the loader's own `linux_read_sorted_physical_devices` step for enumerating zero physical devices, correctly, since none of that hardware exists on this NVIDIA-only host, and Mesa's `llvmpipe` software rasterizer is the sole survivor, confirmed by name in the same trace. That is the `1 devices` the warning has named at every point in this entire investigation, including before the driver upgrade, and it explains why the upgrade alone could never have fixed the symptom, NVIDIA had not participated in the game's own device enumeration at any point up to this fix, regardless of what capability that unreachable device had.

**Root cause.** `docker/unreal/Dockerfile`'s pre-existing, upstream-inherited generation step derives `nvidia_icd.json`'s `api_version` field from `dpkg -s libvulkan1 | grep -oP 'Version: [0-9|\.]+'`, the SYSTEM Vulkan loader package's own instance version, `1.3.204` on this Ubuntu 22.04 base, a number with no relationship to any GPU driver's real capability, coincidental resemblance to the pre-upgrade driver's own version aside. UE's bundled loader (1.4.304, not the system's 1.3.204) requires this field to be present at all costs, full stop, a requirement neither this workspace's own reading of the general Vulkan Loader specification (where the field is documented as optional in current releases) nor the earlier attempt to omit it correctly anticipated; both were corrected only once the loader's own debug trace was consulted directly rather than continuing to reason from the spec in the abstract. The field had always been present, just derived from the wrong source, which is why this defect was invisible through every step of the 5.2 to 5.7 migration and the driver upgrade, until the field was experimentally removed while chasing the (real, but insufficient) extension-gap fix of §16.

**Fix.** `docker/unreal/Dockerfile` gained "NRT delta 7" (`context/unreal-engine-packaging.md` §11.2), hardcoding `api_version` to `1.4.312`, NVIDIA driver `580.173.02`'s own real `apiVersion` as reported by `vulkaninfo`, confirmed by a live run to admit the real NVIDIA device and pass `VP_UE_Vulkan_SM6` outright. The `apt-get install libvulkan1` step is retained, since `vulkaninfo` and other system tooling still need the system loader present, only the version-string derivation from that package is dropped. This value cannot be correctly derived at image build time by any method, since the NVIDIA Container Toolkit mounts the host's actual driver only at container start, never during the build; the Dockerfile's comment records this as a deliberate choice made on the workspace owner's own stated commitment to running this image against driver 580 only, not an oversight, with the field's role as a version floor rather than an exact-match requirement meaning a future driver bump would not itself force this value to be revisited.

**Verification.** Confirmed. The packaged `StonePineForest` client, launched with the corrected manifest in place, passed `Vulkan Profile check complete.` with no criteria warning and reached simulation.

## 18. Harmless startup log lines under UE 5.7 that look alarming but are not, `No SunSky objects found` and the `PixelStreaming` block (2026-08-16)

**Symptom.** A successful `djinn start sitl2` run, `StonePineForest` reaching simulation and streaming camera frames over ROS 2, nonetheless prints several lines that read as failures: `SimPlugin: Error: No SunSky objects found. TimeOfDay settings would ignored/not applied` (twice, once per scene load), `SimPlugin: Error: [AUnrealSimLoader::SetUnrealEngineSettings()] Console variable 'PixelStreaming.WebRTC.DisableResolutionChange' could not be set`, the same for `'PixelStreaming.WebRTC.MaxFps'`, `LogPixelStreaming: Warning: Could not setup hardware encoder... Grepping the 5.7 `Settings.cpp` for every `PixelStreaming.WebRTC.*` CVar it actually registers shows `MaxBitrate`, `DisableTransmitAudio` and `DisableReceiveAudio` unchanged from what the plugin (written against UE 5.1) expects, which is why those three set cleanly with no error, while `MaxFps` was renamed to plain `Fps`, and `DisableResolutionChange` was removed outright with no replacement, which is why exactly those two, and only those two, log the error. Separately, the `Streamer` still exists as `DefaultStreamer` but is never actually started, `no signalling server URL has been set`, since `djinn`'s launch command passes no `-PixelStreamingURL`; the hardware-encoder fallback warning is PixelStreaming probing for an NVENC encoder for a WebRTC session that consequently never opens, consistent with the already-documented fact that `libnvidia-encode.so.1` is not present in this container (`LogCore: Warning: dlopen failed: libnvidia-encode.so.1`).

Critically, none of this touches the path that actually produces the ROS 2 video output. `UUnrealCamera` (`unreal/StonePineForest/Plugins/ProjectAirSim/Source/ProjectAirSim/Private/Sensors/UnrealCamera.cpp`) captures every image type through its own `USceneCaptureComponent2D` objects rendering into private `UTextureRenderTarget2D`s, read back and published over the sim's own `nng`-based topic system (the `scene_camera` / `scene_camera_info` topics seen in the log), a mechanism wholly independent of WebRTC, the PixelStreaming module, and any of the CVars above. PixelStreaming is Epic's own separate browser-streaming subsystem for interactive remote desktop-style access, present in the plugin dependency list but simply unused by this pipeline.

**Root cause.** Two independent, both harmless, facts. (1) `Mountains_Map` has no actor named `SunSky`, so the sim's dynamic time-of-day feature is inert on this map, by content, not defect. (2) `ProjectAirSim`'s `UnrealSimLoader.cpp` was written against UE 5.1's PixelStreaming CVar names, two of which Epic renamed or removed by 5.7; the code's own `FindConsoleVariable() == nullptr` guard converts that drift into a logged `Error` rather than a crash, and PixelStreaming is not part of the ROS 2 video path regardless.

**Fix.** None applied, and none needed. No code or configuration changed as a result of this entry.

**Verification.** Confirmed by direct source inspection, both of the plugin (`TimeofDay.cpp`, `UnrealSimLoader.cpp`, `UnrealCamera.cpp`) and of the exact UE 5.7 engine commit this workspace builds against (`PixelStreaming/Source/PixelStreaming/Private/Settings.cpp`). If dynamic time-of-day control is needed on `Mountains_Map`, add an actor named `SunSky` to the level, a content change, not a code fix; the `PixelStreaming.WebRTC.MaxFps`/`DisableResolutionChange` lines can be silenced by updating `UnrealSimLoader.cpp` to the renamed/removed CVar names, but since PixelStreaming is never started in this pipeline, doing so would only quiet the log, not change behaviour.

## 19. Vulkan device creation failure under `-RenderOffScreen`, SDL3's dummy driver has no Vulkan support at all (2026-08-19, open)

**Symptom.** With §16-§17 closed (driver upgraded to `580.173.02`, `nvidia_icd.json`'s `api_version` hardcoded to match), `djinn start sitl2` now passes `Vulkan Profile check complete.` twice with no criteria warning, selects the real NVIDIA device (`API=1.4.312`, matching the host driver exactly), enumerates its 6 queue families and creates the logical device queue info, then fails immediately after:
```
LogLinux: Warning: MessageBox: Cannot create a Vulkan device. Try updating your video driver to a more recent version.
: Vulkan device creation failed: No dynamic Vulkan support in current SDL video driver (dummy)
LogCore: FUnixPlatformMisc::RequestExit(bForce=true, ReturnCode=1, CallSite=<NoCallSiteInfo>)
```
This is a new, third and currently distinct failure from §16/§17, not a recurrence; the profile check and physical device selection both now succeed, and the failure has moved later, to `vkCreateDevice` itself. `vulkaninfo --summary` and a full `vulkaninfo` run inside the same container, as a separate process, both work correctly and enumerate the NVIDIA device with a live, 256x256 presentable surface, which appears to rule out a purely host/driver-level explanation.

**Investigation.** `Engine/Source/Runtime/VulkanRHI/Private/VulkanDevice.cpp:422-429` (`EpicGames/UnrealEngine` branch `5.7`, commit `0bcfaffa`) shows the MessageBox fires only when `VulkanRHI::vkCreateDevice(...)` itself returns `VK_ERROR_INITIALIZATION_FAILED`; the embedded text `"Cannot create a Vulkan device..."` is UE's own fixed string, unrelated to whatever appears after the second colon. That second part, `"No dynamic Vulkan support in current SDL video driver (dummy)"`, was traced to `libsdl-org/SDL`'s own `src/video/SDL_video.c:2351-2353`, the `SDL_DllNotSupported()` helper (`"No dynamic %s support in current SDL video driver (%s)"`), called from exactly one call site relevant here, `SDL_Vulkan_LoadLibrary()` at `SDL_video.c:6277`, whenever the active SDL video driver's `Vulkan_LoadLibrary` function pointer is null, true of SDL's `dummy` driver by design, since it implements no real windowing backend. `SDL_GetError()` is a persistent last-error string, not scoped to the call that is about to report failure, and `Engine/Source/Runtime/ApplicationCore/Private/Linux/LinuxPlatformApplicationMisc.cpp`'s `GetHeadlessMessageBoxMessage()` (used because `IsSDLDummyDriver()` is true) unconditionally appends whatever `SDL_GetError()` currently holds to the MessageBox text. `VulkanLinuxPlatform.cpp:212`, `bLoadedSDLVulkanLibrary = SDL_Vulkan_LoadLibrary(*FinalVulkanLoaderPath);`, is the call that actually produces this stale error, much earlier in startup (right after `"Using included Vulkan loader."`); its boolean result is stored but never branched on except later at line 225, gated on a wholly separate condition (`!bFoundAllEntryPoints`, from `dlsym`-ing UE's own manually `dlopen`'d loader, not from SDL at all). So the SDL failure at line 212 is real but silently swallowed at the time, and is dead weight, cosmetically alarming but not informative about what actually made `vkCreateDevice` fail. Confirmed all of the profile check, physical device selection, and queue family setup use UE's own manually-loaded Vulkan entry points, not SDL's, which is why they succeed even though `SDL_Vulkan_LoadLibrary` already failed.

Root cause of `SDL_Vulkan_LoadLibrary`, and by extension of why SDL never gets a functioning Vulkan-capable video driver at all in this configuration, traces to `LinuxPlatformApplicationMisc.cpp:320-325`: whenever `-RenderOffScreen` is present on the command line and `SDL_VIDEODRIVER` is not already set in the environment, UE unconditionally hints SDL to the `dummy` driver before `SDL_Init()`, with no fallback and no check for whether a real display is actually reachable. `sitl_ws/scripts/run_airsim.sh` passes `-RenderOffScreen` unconditionally for the `airsim2` target (`iexec airsim2_container ... -RenderOffScreen ...`), and its own header comment records why, upstream issue 75, a dropped `-RenderOffScreen` in a container with genuinely no display previously exited ungracefully. That reasoning no longer matches this container's actual configuration: `sitl_ws/scripts/start.sh:44,48,52` bind-mounts the host's `/tmp/.X11-unix` socket and forwards `DISPLAY` into `airsim2_container`, and the `vulkaninfo` run above proves that mount is live and Vulkan-capable, a real, working X display already exists inside the container, `-RenderOffScreen` is actively discarding it in favour of a driver, `dummy`, that SDL's own source shows has zero Vulkan capability, not merely a degraded one. A commented-out alternative invocation already sits directly below the live one in `run_airsim.sh`, `-windowed` in place of `-RenderOffScreen`, evidence this was anticipated but not yet tried against this specific failure.

The display-connection theory above (that `vkCreateDevice` needs a live SDL windowing connection to succeed) was tested directly and disproven. `run_airsim.sh` was swapped to the commented-out `-windowed` invocation, dropping `-RenderOffScreen` entirely. The resulting log confirms SDL genuinely picked a real driver this time (`LogInit: Using SDL video driver 'x11'`, a real 1920x1080 `SAMSUNG 55"` monitor detected), and `vkCreateDevice` still failed, with the process still exiting via `RequestExitWithStatus(true, 1)`, the identical status code `VulkanDevice.cpp:427` uses right after the `vkCreateDevice` failure MessageBox. No diagnostic text appeared this run only because `LinuxPlatformApplicationMisc.cpp:73`'s `IsSDLDummyDriver()` branch now took the *other* path, `SDL_ShowMessageBox()` at line 218, a real blocking native dialog that cannot be clicked inside a non-interactive `docker exec` session and simply times out silently rather than logging anything, explaining the roughly five-second gap before exit with no error line at all. So `-RenderOffScreen` vs `-windowed`, and `dummy` vs `x11`, is orthogonal to the actual failure; it only changes how the same failure gets reported, gracefully-but-uninformatively under `dummy`, silently under a real driver.

`run_airsim.sh` was reverted to `-RenderOffScreen` (restoring the graceful, non-hanging report path) and re-run with `VK_LOADER_DEBUG=all` exported, the same technique that identified the ICD manifest defect in §17. That produced the real underlying error, previously invisible behind UE's generic MessageBox text:
```
INFO | LAYER:      Failed to find vkGetDeviceProcAddr in layer "libVkLayer_MESA_device_select.so"
DRIVER | LAYER:    vkCreateDevice layer callstack setup to:
DRIVER | LAYER:           Using "NVIDIA RTX 4000 SFF Ada Generation" with driver: "libGLX_nvidia.so.0"
ERROR | DRIVER:    terminator_CreateDevice: Failed in ICD libGLX_nvidia.so.0 vkCreateDevice call
ERROR:             vkCreateDevice:  Failed to create device chain.
```
The `libVkLayer_MESA_device_select.so` line is a separate, benign, expected message, `VK_LAYER_MESA_device_select` is an instance-level filtering layer with no device-level entry points of its own, and the loader logs this same "not found" notice for it on every `vkCreateDevice` call regardless of outcome; it is not the cause. The substantive line is `terminator_CreateDevice: Failed in ICD libGLX_nvidia.so.0 vkCreateDevice call`, the loader's terminator confirming that NVIDIA's own ICD, correctly selected, received the `vkCreateDevice` call and rejected it, with no further reason given at this verbosity; `VK_LOADER_DEBUG` reports that the ICD failed, not why.

**Root cause.** Confirmed narrowed, not yet fully identified. `vkCreateDevice` fails inside NVIDIA's own ICD (`libGLX_nvidia.so.0`), independent of SDL windowing entirely, the `dummy`-driver display-connection theory from this section's first pass is disproven by the `-windowed` experiment above and struck from consideration. The failure is specific to the `VkDeviceCreateInfo` UE 5.7 assembles, since the profile check (`CheckVulkanProfile()`, a separate, smaller device creation via the Khronos Vulkan Profiles library) already succeeds against the same physical device and driver, meaning the full request in `VulkanDevice.cpp`, its extension list, feature-struct `pNext` chain, or both, is what the ICD is rejecting. *(Corrected 2026-08-19: this section's Root cause and Fix originally named the `-RenderOffScreen`-forced `dummy` SDL driver as the suspected cause and proposed switching to `-windowed` as the fix; both were tested directly and shown not to be the cause, see the `-windowed` experiment above.)*

`VK_LAYER_KHRONOS_validation` was then enabled (`VK_INSTANCE_LAYERS=VK_LAYER_KHRONOS_validation`, `VK_LOADER_DEBUG=all` left set) on top of `-RenderOffScreen`, on the reasoning that validation runs its own parameter and spec-conformance checks on the exact `VkDeviceCreateInfo` before the driver ever sees it, and should report a specific violation if one exists. The loader trace confirms the layer inserted correctly (`Inserted device layer "VK_LAYER_KHRONOS_validation"`) and sits in the call chain between `<Loader>` and `<Device>`, and this time the same failure is also promoted to a genuine `UE_LOG` line, `LogVulkanRHI: Warning: *** [Error: General(Loader Message)] terminator_CreateDevice: Failed in ICD libGLX_nvidia.so.0 vkCreateDevice call`, rather than only appearing in the raw loader debug stream. But the validation layer itself emits no error of its own, no `VUID-*` message, no parameter or spec complaint, before the call reaches the driver; it passes the request through unmodified and the ICD still rejects it with the identical opaque failure. This is informative by elimination: the `VkDeviceCreateInfo` UE 5.7 assembles is spec-valid, or at least passes everything `VK_LAYER_KHRONOS_validation` checks, so the rejection is a driver-internal decision, not a malformed request, narrowing the remaining suspects to something validation does not check, most plausibly a specific optional extension or feature the driver advertises as available (as `vkGetPhysicalDeviceExtensionProperties` and the profile check both confirm) but cannot actually satisfy in this container/environment when requested in combination with the rest, `VK_EXT_descriptor_buffer` and the ray-tracing/mesh-shader extension set (`VK_KHR_ray_tracing_pipeline`, `VK_KHR_acceleration_structure`, `VK_EXT_mesh_shader`) being the least common and least exercised of the extensions in the enabled list, and therefore the most likely candidates for a driver-side gap that plain existence-checking (`vkGetPhysicalDeviceExtensionProperties`, the profile check) cannot detect.

**Fix.** Not yet applied. Reverted to `-RenderOffScreen` in `run_airsim.sh`. The next diagnostic step is bisection rather than further log inspection, since both the loader debug trace and the validation layer have now been exhausted without naming a specific cause: (1) re-run with `-noraytracing` (a genuine UE command-line switch that drops the ray-tracing device extensions from the request) to test whether device creation then succeeds, isolating the ray-tracing/mesh-shader extension set as the cause; (2) if that alone does not resolve it, check `ls -la /dev/nvidia*` inside `airsim2_container` to confirm `nvidia-uvm` and `nvidiactl`, not just the render node, are passed through, since some of the suspect extensions rely on unified memory paths that require those device files specifically; (3) check the host's `dmesg`/`journalctl` around the failure timestamp for an NVIDIA Xid error, which would give a definitive driver/hardware-level reason the loader-level trace cannot surface.

**Verification.** Not yet done, pending the above.
