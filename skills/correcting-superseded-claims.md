When a previously written claim, plan, task description, or piece of code is found to be wrong, or is superseded by a later decision, correct it in place rather than layering a new statement after the old one. This rule governs every form of writing and code in this repository, not only the context store described in §1. It applies equally to `plans/`, `ARCHITECTURE.md`, `README.md` files, comments, and any other prose, and to source files, scripts, and configuration.

For documentation, rewrite the paragraph or line so the corrected claim is the only claim offered as primary text, then append a compact note naming what the text previously said, when it changed, and why the old value no longer holds. Do not write a paragraph that restates the old claim, pivots on however to a reasoning sentence, and only then gives the corrected text, and do not follow an unchanged paragraph with a new paragraph describing what has changed. Both leave two claims in sequence for the reader to reconcile, which is the exact confusion the correction note exists to prevent. The correct form is a single, edited paragraph whose first reading is already correct, with the note attached to it rather than trailing it as a separate block.

For code, when a change replaces something because a prior decision it implemented has been superseded, comment out the superseded code in place next to its replacement rather than deleting it outright, with a short comment naming why it was replaced and when. This differs from ordinary refactors or dead-code removal, which stay deleted as usual, since a superseded decision, unlike routine dead code, may need to be recognised again later, or opted back into, by a future session comparing against it. The User upon committing will manually remove the dead code as per their descretion.

This obligation stands independently of git history. A reader working from the file in front of them, not from `git log` or `git blame`, must be able to see the current truth and the decision it replaced without leaving the file. It must be noted that dead code or update documentation will be finalised by the user manually before it is committed so that the user owns responsibility for the changes made and not the AI.
